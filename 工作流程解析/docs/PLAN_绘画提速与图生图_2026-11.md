# 方案：绘画提速 / 智能释放 / 图生图

> 只出方案，不改代码。日期 2026-11-03。
> 结论先行：**45 分钟不是"模型慢"，是显存被语音服务挤爆后 75 倍降速**；而 QQ「文字+图片」这条消息今天根本进不到画图链路（被视觉分支 `return` 截走），所以图生图必须先做路由改造。

---

## 0. 摘要

| 项 | 现在（实测） | 目标（不改观感） | 主要手段 |
|---|---|---|---|
| pro 1080×1440 | 195 / 202 s | 90~120 s | USDU 几何 + detailer 缩放 + 去掉重复装载 |
| pro 1024×1024 | 106 s | 55~70 s | 同上 |
| 最坏情况 | 42~47 min | < 6 min（或明确"等显存"而不是静默变慢） | 显存预检 + 单并发 + 绘画租约 |
| 冷引擎首图 | +60~180 s | +2~5 s | 意图预热 + 引擎常驻策略 |
| 改图 | 重掷一张"像的" | 在原图上改（保构图） | img2img 复用同一套图构造 |
| QQ「文字+图」 | 只得到看图点评 | 图生图 | 路由闸门 + img2img 图 |

三条互不干扰的实施线：**L1 消抖（最大收益、零质量影响）→ L2 减计算（对齐官方参考工作流）→ L3 图生图（新能力）**。

## 1. 现状测绘（有证据）

### 1.1 完整链路

```
QQ 文本消息
  └─ napcat/analysis/analysis_core.py:61  规则词硬触发（零 LLM）
     └─ painting_core.py:171 dispatch_qq → :185 _open（按 channel 冷却、起线程）
        └─ :237 _run
           ├─ prompt_producer.run()       提示词 LLM（thinking，最多 3 次重试 + 法典自检）
```

链路本身没问题，问题都在**时间**和**入口**上。

`logs/comfy_engine.log` 的 `Prompt executed in` 全集：

### 1.3 那两次 40 分钟到底慢在哪

**47 分钟那次**（log 第 3306 行起）——基础采样就吃掉全部时间：

```
loaded completely; 4506.89 MB usable, 3988.40 MB loaded, full load: True
  1/30 [01:13<35:25, 73.31s/it]     ← 正常是 1.0 s/it
 30/30 [37:30<00:00, 75.35s/it]
Prompt executed in 00:47:29
```

30 步 × 75 s = **37.5 分钟**，随后 VAE 直接装不下：

```
Requested to load WanVAE
loaded partially; 0.00 MB usable, 0.00 MB loaded, 242.00 MB offloaded
```

**42 分钟那次**（第 3150~3301 行）——采样正常但分块重绘被拖慢 5 倍：

```
USDU: 30tile [07:34, 15.28s/tile]      ← 2160×2880，tile 512/padding 256 → 6 行 × 5 列
...
Prompt executed in 00:42:06
```

关键线索：`Total VRAM 8151 MB`，而采样前只有 `4506 MB usable` ⇒ 当场**已有约 3.6 GB 显存被别的进程占着**；日志里还出现 `lowvram patches: 1053`、`lowvram patches: 1492`。

### 1.4 谁在吃显存

| 进程 | 证据 | 驻留特征 |
|---|---|---|
| ComfyUI（绘画） | 4.0 GB UNET + 1.1 GB 文本编码器 + 0.24 GB VAE ≈ **5.3 GB** | 只在出图期间驻留，结束后卸到内存（`Unloaded partially: 3700 MB freed`） |
| GPT-SoVITS（TTS） | `.vendor/.Sovits/start.bat` → `api_v2.py`，`inference_webui` 启动即把 BERT/SSL/T2S/VITS/BigGAN 全 `to(cuda)`、`is_half=True` | **常驻**，没有 unload 接口 |
| SenseVoice（ASR） | `.vendor/.SenseVoice/start.bat` 写死 `--device cuda` | 常驻 |
| 浏览器 / 桌宠 / 其它 | Windows 桌面正常占用 | 波动 |

8 GB 卡上 5.3 GB（绘画）+ 1.5~3 GB（TTS）+ ~0.5 GB（ASR + CUDA context）本来就超了。WDDM 允许显存超卖到系统内存，于是**不报错、只变慢**——75 s/it 就是权重/激活在 PCIe 上来回搬。

> 这一条同时解释了三件事：为什么"有时候 3 分钟、有时候 40 分钟"、为什么 `fast` 档也会偶发很慢、为什么 42 分钟那次 VAE 都装不下。

### 1.5 另外两个隐形成本

1. **每次绘画都新建 connector**：`painting_core.py:370` 里 `create_connector(self.config)`，`base.py:126 object_info()` 的进程内缓存随之丢弃 ⇒ 每次最多多一次 20 s 的 `/object_info` 超时探测。
2. **自家人抢 GPU**：`_open()` 里立刻起 `_qq_opener` / `_live_opener` 线程（`painting_core.py:225-232`），live 渠道会当场调 TTS ⇒ **采样刚起步就触发 SoVITS 推理**，自己把自己挤下显存。

### 1.6 一个必须排除的嫌疑

`config.yml` 现在是 `comfy.mode = external`（用外部实例），但内置内核是"**常驻、不随主程序退出**"设计（`comfy_painter.py:2-5`，`.vendor/.ComfyNode/engine.pid` 还留着 `pid 30736 / 2026-10-31`）。如果切换模式时内置内核没被 `stop()`，就会有两个 ComfyUI 各扛 5 GB。**这一点必须先测**（见 L0）。

## 3. L1：把 75 倍降速这条路堵死（收益最大，质量零影响）

### 3.1 全局单并发

现在 `is_painting()` 按 channel 判（`painting_core.py:73`），live + 群 A + 私聊 B 可以同时开三张，在 ComfyUI 里排队但它们**同时存在**，显存直接爆。

- 新增 `engine.single_job`（默认 true）：全局只允许 1 张在跑，其余进队列并明确回一句（"前面还有 1 张，画完就到你的"）。
- 画板按队列显示 `1/2`，避免"发了没反应"。

### 3.2 绘画租约（把自己人的 GPU 占用让开）

- `engine.defer_tts_during_paint`（默认 true）：采样期间**不调 TTS**。开场白 / 画完后点评在 QQ 渠道本来就是纯文字，live 渠道改成"上板文字 + 出图后一起念"，或把 TTS 排进 job 结束后的队列。
- 出错播报 `_say_need` 同样延后到 job 结束。
- 不碰 ASR（用户说话必须能听见），但 ASR 是短促 burst，影响远小于常驻的 TTS。

### 3.3 提交前显存预检 + 快速失败

```
free = nvidia-smi 查询可用显存
if free < engine.min_free_vram_gb (默认 5.6):
    ① 尝试空闲释放（L2）
    ② 等 engine.wait_for_vram_sec（默认 45 s），每 5 s 复测
    ③ 仍不足 → 不硬跑，画板显示"等待显存"，日志写明占用者 PID
if free >= 阈值:
    正常提交
```

要点：**宁可等 30 秒，也不要静默 75 倍慢**。现在用户看到的是"发了没反应，40 分钟后突然出图"，体验比明确提示差得多。

### 3.4 引擎启动参数

| 参数 | 现在 | 建议 | 理由 |
|---|---|---|---|
| `--reserve-vram` | 未设 | `0.8` | 别把最后 1 GB 也吃干净，减少 WDDM 换页概率 |
| 显存模式 | 默认 `--normalvram` | 保持 | 4 GB 底模 + 8 GB 卡，`--highvram` 会更频繁 OOM |
| `PYTORCH_CUDA_ALLOC_CONF` | 未设 | `expandable_segments:True` | 减少碎片导致的"明明有地方却装不下" |
| `--fast` / `--use-sage-attention` | 未开 | **保持不开** | ComfyUI 官方对 `--fast` 的说明就是 "potentially quality deteriorating"；sage 需单独 A/B，列为 L5 选做 |
| `--disable-smart-memory` | 未开 | **保持不开** | 开了会让模型常驻显存，8 GB 上反而更容易爆 |

外加一条系统级设置（一次性、可回滚）：NVIDIA 控制面板 → 为 `runtime\312\python.exe` 设置 **CUDA - Sysmem Fallback Policy = Prefer No Sysmem Fallback**。让"装不下"变成可捕获的报错，而不是 75 倍慢——配合 3.3 的预检就变成可解释的等待/重试。

### 3.5 常驻对象 + 预热

- `create_connector()` 结果按 `(mode, host, port, node_dir)` 缓存到进程级，`object_info` 跟着复用；引擎重启时用 `/system_stats` 版本号失效。
- **意图预热**：命中绘画规则词（`analysis_core.py:61`）或提示词 LLM 刚开始调用时，后台并行 `start()`。现在是提示词生成完了才 `_ensure_comfy()`（`painting_core.py:364`），冷启动 60~180 s 全砸在用户等待里。
- 预热后可选送一个 1 步 64×64 温任务（约 2 s），把 UNET/TE/VAE 提前装进显存，第一张少等 5~10 s。

### 3.6 端到端时间线日志

现在只有 `本次耗时 202s` 一个数，无法定位慢在哪。改成一行结构化日志：

```
[paint_timeline] ch=qq_group_x prompt=18.4s(含1次重试) engine_wait=1.2s queue=0.0s
                 sample=64.8s usdu=92.1s detailer=21.3s save=1.1s total=199.0s peak_vram=6.9GB
```

有了它，P2 的参数调整才有依据，也能直接回答"8 分钟里到底谁占的"。

## 4. L2：pro 链路减计算（对齐官方参考工作流，观感不变）

### 4.1 参考工作流 vs 现在的 pro 链

`.vendor/.ComfyNode/node/workflow.json`（画师原工作流，观感基准）的实际参数：

| 项 | 参考工作流 | 现在 pro | 差异 |
|---|---|---|---|
| 基础采样 | 30 步 / cfg 5 / er_sde / simple | 同 | 一致 |
| 放大 | `UpscaleModelLoader` **被 bypass** | 4x-AnimeSharp + ImageScale 2x + nearest-exact | 多一次 4x 放大再缩 |
| 分块重绘 | `UltimateSDUpscale` **被 bypass**；节点参数为 tile **1024×1400** / padding **32** / mask_blur 8 | tile **512×512** / padding **256** / mask_blur 32 | **重叠率从 ~3% 抬到 75%，块数 ×3** |
| 局部细化 | 无 | hand/face/eye 三段，guide 1536 | 参考流程没有 |

也就是说：现在的 pro 比"原作者认为的成品"多做了 2~4 倍的计算，其中 USDU 的几何参数还偏离了原作者自己填的值。

### 4.2 调整项（每一项都单独 A/B）

| # | 改动 | 预期省时 | 观感风险 | 依据 |
|---|---|---|---|---|
| 1 | `usdu.tile 512/pad 256` → `1024/pad 64` | 分块阶段 **×2.5~3** | 中（需 A/B 看接缝） | 参考工作流自己用 1024×1400/pad 32；更大的 tile 对 1024 原生模型上下文更完整，通常**更少接缝** |
| 2 | `detailers.*.guide_size/max_size 1536 → 1024` | 细化阶段 **×2** | 低 | 局部重绘是把 bbox 裁切后放大到 guide 再缩回，1024 已远超实际人脸/手部像素；配置默认值本来就是 768/1280 |
| 3 | 单图 detailer 段数上限（手 ≤2、脸 1、眼并入脸） | 细化阶段再 ×1.3 | 低 | YOLO 误检出多个小手时，现在每个都跑 20 步 |
| 4 | `usdu.steps 20 → 12` | 分块阶段再 ×1.4 | 中 | denoise 0.15 下有效步数本来就少；**必须 A/B** |
| 5 | 4x 放大模型 → 2x 再缩放 | 几秒 | 低 | 4x 再 lanczos 缩到 2x 是浪费，但不是瓶颈，优先级最低 |
| 6 | 基础采样上先发一张 1024 预览，再走 05/06/07 | 0（感知收益大） | 无 | 最终图完全不变；用户 30~60 s 就能看到画面 |

**不动的**：sampler / steps / cfg / shift / quality_prefix / negative_prompt / LoRA 链 / canvas_sizes。这些是观感开关，一个都不碰。

### 4.3 为什么不用"降步数/量化"来提速

- 基础采样 30 → 20 步：细节和构图稳定性会明显变化（这是最直观的质量差），排除。
- fp8 / GGUF 量化底模：质量有损，排除。
- 换更小的底模：等于换画风，排除。
- `--fast` / sage-attention：前者官方标注可能降质；后者数值路径不同，只作为 L5 选做，A/B 通过才上。

## 5. L3：智能释放（先把预期校准）

先纠正一个常见误会：**ComfyUI 空闲时本来就会把模型卸到内存**（日志 `Unloaded partially: 3700 MB freed, 288 MB remains loaded` 就是它自己干的）。所以"闲置释放"释放的是：

- Torch 缓存池 + CUDA context：**约 0.5~1.5 GB**（`/free {free_memory:true}` 能立刻归还）
- 宿主内存里的模型副本：**约 1~3 GB**（只有停进程才还）

真正长期吃显存的是 **SoVITS 的常驻模型**，而它没有 unload 接口。所以释放策略分三层：

### 5.1 温层（默认开启，空闲 60~90 s）

`POST /free {"unload_models": true, "free_memory": true}`，把显存还回驱动，进程保留。

**坑（实测代码）**：本内核的 `/free` 只往队列 flag 里塞值（`server.py:961`），而 flag 只在 worker **取到任务之后**才被读（`main.py:254`）；空闲时 worker 卡在 `q.get(timeout=1000)`（`execution.py:1127`），`set_flag` 也不会 `notify`。所以**空闲引擎调 `/free` 最多要等 1000 秒才生效**。

两个解法（二选一，见第 8 节待确认）：
- **A（推荐）**：给 `execution.PromptQueue.set_flag` 加 3 行 `notify`，与项目已有的 `_patch_align.py`（同样改 vendor 内 Impact Pack）同机制，可重复执行、可校验；
- **B（零侵入）**：调完 `/free` 再投一个 `EmptyImage(16×16) → PreviewImage` 的唤醒任务。零计算量，但会在 output 目录留小文件，需要顺手清理。

### 5.2 冷层（空闲 30~60 min，或显存告急时）

按 `engine.pid` 结束引擎进程（`comfy_painter.stop()` 已实现），把 CUDA context + 宿主内存全部归还。代价是下次冷启动 60~180 s，用 3.5 的"意图预热"抵消：用户话还没说完，引擎已经在起。

### 5.3 对 SoVITS（不动 vendor 代码也能做）

- `engine.defer_tts_during_paint=true`（默认）：绘画期间自家人不调 TTS —— 这条能消掉**大部分**自伤。
- `engine.release_tts_before_paint=false`（可选，默认关）：绘画前重启 SoVITS 让它空转，画完第一次说话多等 10~20 s。8 GB 卡上这是唯一能彻底腾出 1.5~3 GB 的办法，但代价明显，交给用户按场景开。
- 长期解法（不在本次范围）：给 SoVITS 加 `/unload`，或干脆与 ComfyUI 做端口级排队（同一进程按需装载）。

### 5.4 面板可见

画板 / 工具箱加一个引擎状态：`热（模型在显存）/ 温（模型在内存）/ 冷（进程停止）/ 忙 / 等待显存`，附当前可用显存。用户一看就知道"为什么慢"。

## 6. L4：图生图

### 6.1 现状：QQ「文字+图片」根本到不了画图

- **私聊**：`napcat_core/event_handler.py:69-102`，只要消息里有图就调视觉并 `return`。
- **群聊**：`qq_response.py:292-302`，`at_self and images` 也走视觉并 `return`。
- 也就是说："发一张图 + 『照这张画一张』"今天只会换来一段看图点评，**画图工具压根没被调用**。
- 而"画完 120 s 内改图"走 `edit_router → continue_paint`（`painting_core.py:121-137`），是**纯 txt2img 重掷**，每改一次都是"重新画一张像的"，不是改这张。

### 6.2 路由改造（最小侵入）

在两条图片分支**之前**加一个绘画闸门：

```python
if images and paint_intent(merged_text):     # 规则词命中，零 LLM
    -> 走绘画（带 source_images），不走视觉
else:
    -> 原视觉链路不变
```

- `paint_intent` 复用 `analysis_core.PAINT_RULE_WORDS`（已有 300+ 匹配词），抽成公共模块供私聊/群聊共用。
- 兜底防误伤：命中规则词但同时含「看看/这是啥/好看吗/评价一下」且无「画/画成/改成」动词 → 仍走视觉；或给 analysis 的 LLM 增加一个 `flux_paint(use_image=true)` 签名（多花一次 LLM，默认关）。
- 开关：`img2img.qq_enabled`（私聊/群聊可分别）。
- 图片落盘**用原图**：新增 `TBImageSearch.prepare_for_paint()`（EXIF 旋转 → RGB → 长边限制 → 对齐 16），与 `prepare_for_vision()` 分开——后者按 2 MB 压缩、按 5 张截断，拿来当底图会被压花。

### 6.3 图生图构造

```
POST /upload/image  (multipart) → 内核 input 目录里的文件名
  → LoadImage
  → ImageScale（crop/pad/stretch 到目标画布，默认 crop）
  → VAEEncode
  → KSampler(denoise = strength)        ← 替换 build_graph 里的 EmptyLatentImage
  → [05 放大 → 06 USDU → 07 detailer 不变]
  → VAEDecode → SaveImage
```

实现上代价最小的做法：给 `build_graph()` / `build_pro_graph()` 加一个 `latent_src=None` 参数（`base.py:66` / `:176`），后半段一行不改。

### 6.4 strength 怎么定（比换模型更影响成败）

| 用户话术 | strength | 效果 |
|---|---|---|
| 「照这张画」「按这张」「同款」「参考一下」 | 0.35~0.45 | 保构图/姿势，换笔触与上色 |
| 「改一下」「换成」「加上」「去掉」 | 0.50~0.65 | 中等改动 |
| 「画成…」「变成…」「风格化」 | 0.70~0.85 | 大改，只借构图 |
| 未表态 | 0.60 | 默认 |

让提示词 LLM 在现有 JSON 里多输出一个 `strength` 字段最省（`prompt_producer` 已经在产出 positive/cinema/canvas/title/character）。

### 6.5 源图喂给提示词（关键，避免"图和词打架"）

复用现成的视觉桥（不写记忆、不发消息）：

```python
TBNapCatVisionActive().process([src], "", meowid, need_description=True, write_memory=False)
→ {"description": ...}
```

把 `description` 作为 `prompt_producer.run(source_desc=...)` 的新输入：
- 原图已有的角色/构图/配色不要再重复描述，LLM 只描述"要变的部分"；
- 原图能识别出角色时，顺手填 `character`，走现成的角色词典。

### 6.6 顺手把"改图"升级成真改图

`continue_paint` 现在只是换提示词重掷。改成：以 `last_paint["final_image"]` 为 source，strength 0.45~0.6 → 真正"在这张上改发型/换衣服/补耳朵"。

这一条本身就是现有功能的**质量大补丁**（日志里 22:50 那次"把头发改为白色、耳朵改为橙色"就是重掷，观感必然跳）。

## 7. 质量守护（因为你明确要求"不能影响质量"）

新增 `scripts/paint_bench.py`：

1. 固定 10 组 prompt + 固定 seed + 固定画布（1024×1024 / 1080×1440 各 5 组）。
2. 同一台机器、同一时段，跑 `baseline`（当前参数）与 `candidate`（待验证参数）。

5. 输出 `工作流程解析/docs/paint_bench_<date>.md` + 并排对比图。

**验收线（全部满足才算过）**：
- a) 脸部/手部 1:1 裁切无可辨认的劣化；
- b) 大图接缝处无新增接缝或糊块；
- c) 10 组平均耗时达到目标（pro 1080×1440 ≤ 130 s）；
- d) 10 组 0 张崩图、0 次"等待显存"超时。

**只叠加通过的项目**，每个 knob 单独开一次 A/B，配方不打包上线。

## 10. 风险与红线

1. **`.vendor/` 是只读区**：L3 温层要实时释放，需要在 `ComfyUI/execution.py` 加 3 行 `notify`（与现有 `_patch_align.py` 改 vendor 内插件同机制）。不点头就走"空任务唤醒"方案，副作用是 output 目录多小文件。
2. **USDU 几何调整必然改变像素**（接缝位置/细节分布会变），所以只用 A/B + 人眼验收，绝不"看着差不多就上"。
3. **全局单并发**会改变"多群同时画"的体感（从并行变排队），但现在的"并行"实际是互相拖慢。
4. **SoVITS 常驻显存无法从 Python 侧优雅卸载**，只能靠"绘画期间不自调 TTS"缓解；要彻底解决得给 SoVITS 加 `/unload` 或做端口级排队，属于另一个改造。
5. **img2img 的 strength 是双刃剑**：过低"几乎没动"、过高"面目全非"。必须有默认值 + 一句"再像一点/改多点"的回调（走 `edit_router` 调 strength）。
6. **质量红线**：sampler / steps / cfg / shift / quality_prefix / negative_prompt / LoRA / canvas 一律不动。
