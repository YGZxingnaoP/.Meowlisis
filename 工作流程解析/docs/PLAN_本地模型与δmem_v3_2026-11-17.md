## 1. 现场审计：MeowLLM 现在是什么状态

### 1.1 硬件与运行形态

- 本机：**RTX 5060 Laptop，8 GB 显存**（`nvidia-smi` 实测 8151 MiB）。
- MeowLLM 是独立 sidecar：OpenAI 兼容 HTTP + 控制面，默认 `127.0.0.1:18100`。
- 当前只注册了两个引擎：`stub` 和 `dualstream`（`meowllm/engine/factory.py`）。
  `start.bat llamacpp` 是旧入口，factory 里**没有** `llamacpp` 引擎；`llama.cpp/` 目录目前也是空的。
- 本地权重只有 `Qwen3-0.6B` 和 `models/dmem-261018`；没有 8B 权重。
- 主项目 12 族端口全部用 OpenAI SDK 构造，理论上只改 `base_url` 就能接管；但 `DmemBridge` 会调
  `/meowllm/control/dmem/*`，换到纯 `llama-server` 后这些控制面端点不存在，必须先关 δ-mem 或加代理。

### 1.2 主链路真实负载（决定“8B 够不够”）

从现有文档与配置看：

- `llm.short_term_rounds: 40`；真实请求出现过 **200 条消息 / 11k 字符 / 15 个工具**；
- `n_ctx: 8192`，服务端会把历史裁到约 4k token；
- 主对话是角色扮演 + 情绪 + 工具 + 记忆摘要混合，system prompt 约 4.7k 字；
- 工具调用走 `func/toolbox/`，工具 schema 多、参数嵌套，9B 模型容易格式错；
- `reasoning_content` 在部分端口被真实消费，但主对话并不强依赖。

结论：**8B 能接主对话，但不能原样接“4.7k 字 system + 40 轮 + 15 工具”**。
必须先把 prompt 压到 1.5–2k 字、历史 12–16 轮、工具按需注入，否则 9B 的注意力会被稀释，
表现会比 0.6B 好不了多少。

### 1.3 δ-mem 这一版的硬事实

`models/dmem-261018` 是当前本机权重，训练日志与 eval 写得很清楚：

| 项 | 值 |
|---|---|
| 训练样本 | 1835（训练 1744，留出 91） |
| 数据来源 | `real/locomo: 1307`、`abstract_memory/template: 438`、`neutral: 90` |
| context | p50=768，max=768（截断） |
| answer | p50=11 token（极短） |
| 结构 | 36 层，r=64，N=1，chunk=16，56.63M 可训参数（0.69%） |
| 训练 | 872 步，batch=1，accum=2，lr=2e-4，峰值 17 GiB，约 31 分钟 |
| 留出集 | no-context 7.6435，with-state 2.9832，**gap 4.6603** |

这个 gap 看起来“很成功”，但它恰好是**危险信号**：no-context NLL 高到 7.64，说明模型在
“没有状态”时几乎不会写这条 response；with-state 降到 2.98，说明状态承担了大部分语言建模。
这不是“记住了事实”，更像是“把答案/上下文压进了状态”。换一个 OOD 状态，模型就会照着噪声写。

### 1.4 为什么“注意力彻底崩坏”：8 条根因

> 下面每条都能在代码/日志里找到对应证据。不要把问题归因于“数据不够多”——这一版是**分布错位**，
> 不是量不够。

| # | 症状 | 根因 | 证据 | 修法 |
|---|---|---|---|---|
| 1 | 换中文角色扮演就胡言乱语 | **训练/推理格式不一致**：训练是 LoCoMo 英文 `speaker: text` + 中文事件行；生产是 `[时间]\n用户：...\n我：...` | `build_from_real.py::session_text`、`dmem_bridge.py::_compose` | 训练 context 必须逐字复刻生产 `_compose` 格式，中文为主 |
| 2 | 前几轮还行，越聊越崩 | **写入 regime 不一致**：训练只写一次 context 从空状态开始；生产每轮 `append`，状态被写几十次 | `train_sft.py` 单次 `write_state`；`dmem_bridge` 每轮 append | 训练要模拟 1/5/20/50 次写入后的状态；按时间线顺序写 |
| 3 | 状态里“用户”和“我”混在一起 | **chunk 不按消息边界**：`segments` 字段存了但训练完全没用，固定 16 token 切 | `dataset.py` 存 `segments`；`train_sft.py` 不传 `boundaries`；`layer.pool_chunks` 默认固定 chunk | 按每条消息/每个语义段写一次（SSW 的原意），不要跨角色平均 |
| 4 | α 调大就重复、调小就没记忆 | **注入无界**：`log_alpha` 自由 exp，`w_dq/w_do` 全秩 64→q_dim，没有 gate/上限；训练会把它推到“靠状态偷懒” | `layer.py::steer`、`reset_parameters`；`api.md` 的 α 表 | 零初始化 + gate + `tanh` 有界 + α 上限；中间层、r=8–16 |
| 5 | 干净短 prompt 有效，真实长 prompt + 工具就崩 | **训练目标只教“没有 context 时用状态”**，没教“有 context 时怎么共存” | `train_sft.py` 的 loss 只在 context 被删掉时算 | 50% 样本保留 context；加 KL 保底；加“状态无关/冲突”负样本 |
| 6 | 留出集 gap 很大，但上线不可用 | **评测错位**：只测 no-context vs with-state，不测生产态（context + state）、不测退化/工具/虚假记忆 | `evaluate()` 只有两臂；91 条留出 | 加生产态评测、通用 ppl、4-gram 重复、空回复、工具格式、false-memory |
| 7 | 回复变“短答机器/八股” | **数据分布**：answer p50=11 token，LoCoMo 问答为主，没有偏好/约束/更新/闲聊样本 | `train.log` 数据画像 | 加偏好、约束、时间更新、冲突、闲聊锚点；response 长度分布要像聊天 |
| 8 | 错误会自我强化 | **把模型自己的回复写进记忆**：`我：<reply>` 里的错误猜测下一轮被当事实读回 | `dmem_bridge.py::_compose` | 只写用户事实 + 已验证承诺；助手回复打 `source=assistant` 低权重，或干脆不写 |

一句话：**这一版不是“记忆算法失败”，是“训练时的记忆”和“生产时的记忆”不是同一个东西。**
在这种错位下，α 越大，错得越狠；α 越小，越像没装。所谓“很窄的强度窗口”就是错位的直接表现。

## 2. 本地模型选型

### 2.1 约束

- 8 GB 显存，Windows，单卡；
- 中文聊天/角色扮演优先，工具调用次之；
- 量化可接受（Q4_K_M）；
- 不要求双流 KV，不要求多模态；
- 要能通过 OpenAI 兼容接口接入现有 12 个 port。

### 2.2 候选对比（工程判断，非排行榜）

| 模型 | 参数 | Q4_K_M | 中文聊天 | 角色扮演 | 工具 | 8 GB | 结论 |
|---|---:|---:|---:|---:|---:|---|---|
| **Qwen3.5-9B**（post-trained） | 9B | 5.68 GB | ★★★★★ | ★★★★☆ | BFCL-V4 66.1 / TAU2 79.1 | ✅ 16K | **主选** |
| Qwen3.8-9B-Distill | 9.65B | 5.78 GB | ★★☆（英文向） | ★★☆ | 中上 | ✅ 16K | 想要更新知识/推理时试 |
| Ministral-8B-Instruct | 8B | ~5 GB | ★★ | ★★★ | ★★★★ | ✅ | 工具/指令强，中文弱 |
| Qwen3.5-4B | 4B | ~2.5 GB | ★★★★ | ★★★ | 中 | ✅✅ | 速度兜底 |
| Gemma 4 12B Unified | 12B | ~7 GB | ★★ | ★★★ | 中 | ⚠️ 很紧 | 不推荐本机 |
| Qwen3.8-27B | 27B | ~16 GB | ★★★★★ | ★★★★★ | ★★★★★ | ❌ | 云端/大卡 |

> 关于“只看 2026-09 之后”：我把 9–11 月的新 8B 也扫了一遍。
> **MiniMax M3-mini / M3.1-Flash**（2026-10）走的是 MoE + 长上下文 Agent 路线，生态和 GGUF 还不稳；
> **WeDLM-8B-Instruct**（2026-10 社区转发，模型本身更早）是扩散/并行解码路线，不适合直接塞进
> 现有 OpenAI 流式链路；**TwIL-8B**（2026-11）偏数学/代码，不是聊天模型。
> 因此在“8 GB + 中文聊天/角色扮演 + llama.cpp + OpenAI 兼容”这四个约束下，
> **Qwen3.5-9B 仍是主选**；最新的可用备选是 2026-08 的 **Qwen3.8-9B-Distill**（英文向，需实测中文）。

### 2.3 为什么是 Qwen3.5-9B

- **架构友好**：32 层 = 8 ×（3 × Gated DeltaNet + 1 × Full Attention）。只有 8 层全注意力，
  16K 上下文的 KV 很小；8 GB 卡跑 Q4_K_M 仍有余量。这正好吃到你“取消双流、量化也行”的窗口。
- **中文强**：C-Eval 88.2、MMLU-ProX 76.3、NOVA-63 55.9；官方支持 201 种语言。
- **角色扮演可用**：公开测试里“多角色切换/深海驾驶员”这类用例能到 86 分级别；不是 RP 特化模型，
  但底座足够，后面用 LoRA 补风格。
- **工具不残**：BFCL-V4 66.1、TAU2-Bench 79.1；比 4B 强很多，复杂 schema 仍需约束/少样本。
- **GGUF 生态全**：unsloth 官方量化，Q4_K_M 5.68 GB，Q4_K_S 5.39 GB，Q3_K_M 4.67 GB；
  llama.cpp 已合入 Qwen3.5 支持（PR #19468），Ollama 也有 `qwen3.5:9b`。
- **许可证**：Apache 2.0。

> 为什么不是 Qwen3.8-9B-Distill：它是 Qwen3.8 2.4T A95B 蒸馏进 Qwen3.5-9B 架构，
> MMLU 0.546 → 0.751，知识/推理更强；但模型卡语言标的是 **en**，中文角色扮演不保证。
> 可以下下来做 A/B，但不要默认它比 Qwen3.5-9B 更适合你。

### 2.4 下载与部署

```powershell
# 1) 模型（HF 镜像；5.68 GB）
$env:HF_ENDPOINT = "https://hf-mirror.com"
hf download unsloth/Qwen3.5-9B-GGUF Qwen3.5-9B-Q4_K_M.gguf `
  --local-dir D:\.Meowlisis\.vendor\.MeowLLM\models\Qwen3.5-9B-GGUF

# 2) llama.cpp：用带 Qwen3.5 支持的新版（b11669 之后；CUDA 构建优先）
#    https://github.com/ggml-org/llama.cpp/releases

# 3) 起服务（plain，单流，关 thinking）
llama-server.exe `
  -m D:\.Meowlisis\.vendor\.MeowLLM\models\Qwen3.5-9B-GGUF\Qwen3.5-9B-Q4_K_M.gguf `
  --host 127.0.0.1 --port 18100 `
  -c 16384 -b 512 -ub 512 -ngl 99 -np 1 `
  -fa on -ctk q8_0 -ctv q8_0 `
  --jinja --reasoning-format none `
  --temp 0.7 --top-p 0.9 --top-k 20 --repeat-penalty 1.05
```

要点：

- `-c 16384` 先稳；OOM 就 `-c 8192`，或 `-ctk q4_0 -ctv q4_0`。
- `-np 1`：单卡单 slot，避免两个 QQ 会话互相抢显存；并发靠队列。
- `--jinja`：用模型自带 chat template；Qwen3.5 默认 thinking，必须用
  `--reasoning-format none` 或请求里 `chat_template_kwargs: {"enable_thinking": false}` 关掉。
- `--repeat-penalty 1.05` 只是兜底；真正防重复靠 prompt + 数据 + 评测。
- 8 GB 卡上 Q4_K_M + 16K + q8 KV 大约 **6.2–6.5 GB**，给桌面留 1 GB 左右；
  如果 Windows 桌面占用高，降到 `-c 12288` 或 Q4_K_S。
- 速度预期：**桌面 5060 约 40–46 tok/s；笔记本 5060 约 17–25 tok/s**（社区实测差异大，以你机器为准）。
  256 token 回复约 10–15 秒；QQ 聊天建议 `max_tokens=128–192`，先保证响应。

### 2.5 它能取代什么、不能取代什么

| 主链路域 | 本地 9B | 建议 |
|---|---|---|
| `func/llm` 主对话/角色扮演 | ✅ 可以 | P0 先切 |
| `func/llm_active` 主动对话 | ✅ 可以 | P1 |
| `func/toolbox` 工具调用 | ⚠️ 部分 | 简单工具本地；复杂/多步保留 API |
| `catbrain/AbstractMem`、`UserMemory` 抽取 | ✅ 可以 | 用 JSON schema 约束 + 少样本 |
| `catbrain/CatValues`、`psyche` | ⚠️ 可以但需评测 | 先影子 |
| `meowsinger` 歌词 | ✅ 可以 | 直接换 |
| `database.search` 网页摘要 | ⚠️ 长文弱 | 保留 API 或 4B 摘要 |
| `database.store` embedding | ❌ 不做 | 保留 bge/云端 |
| `meowvision` 视觉 | ❌ 不做 | 保留 API |
| `flux_painter` 绘图 prompt | ⚠️ 可以 | 先 A/B |

**结论**：8B 级本地模型是“主对话替身”，不是“全栈替身”。要 100% 取代 API，得 27B/云端，
或者接受复杂任务质量下降。最稳的是**路由**：本地优先，低置信/工具重/长文/视觉走 API。

## 3. 取消双流后的接入方案

### 3.1 生产路径：llama-server 直接顶上去

你现在的 12 个 port 都是 OpenAI SDK；把 `base_url` 指到 `http://127.0.0.1:18100/v1` 即可。
不需要 MeowLLM 的 OpenAI 层，也不需要双流 KV。

```yaml
llm:
  local_llm_type: deepseek        # 复用现成 port 类，不改代码
  deepseek:
    base_url: http://127.0.0.1:18100/v1
    api_key: local
    model: qwen3.5-9b
    stream: true
```

注意三件事：

1. **`extra_body.meowllm` 会被 llama-server 忽略**。`top_k`/`repeat_penalty` 放请求顶层，
   llama.cpp 的 OpenAI 兼容层认这两个；`meowllm` 子块不认，但一般会被忽略，不会 400。
2. **`DmemBridge` 先停**。它每轮 POST `/meowllm/control/dmem/write`；纯 llama-server 没有这个端点，
   会 404/连接失败。要么 `memory.delta_mem.enabled: false` 且不实例化 bridge，要么加一个 404 兜底。
3. **`/meowllm/control/*` 的统计/健康检查**如果前端在用，保留 MeowLLM 作为“控制面 + 实验面”，
   业务流量走 llama-server；或者写一个薄代理，把 `/v1/*` 转发到 llama-server，控制面留空。

### 3.2 提示词重构（比换模型更影响体感）

当前 system prompt 4.7k 字 + 40 轮历史 + 15 工具，9B 会被稀释。建议：

| 块 | 现状 | 建议 |
|---|---|---|
| 角色卡 | 含情绪，位置最前，每轮变 | 拆成“稳定人设”（800–1200 字）+“当前情绪”（200 字，放最后） |
| 前置词/后置词 | 两套约束可能冲突 | 合并成一份“行为优先级”，不超过 300 字 |
| 短期记忆 | 40 轮，混多模块条目 | 12–16 轮；工具/绘画/唱歌条目单独块，不进对话历史 |
| 长期记忆 | 30 条摘要 | 检索 5–10 条，按“事实/偏好/约束/时间”分区 |
| 工具 | 15 个全量 | 按意图注入 3–5 个；其余用 `tool_choice` 强制/禁止 |
| 时间/情绪 | 在角色卡里 | 移到 prompt 末尾，保前缀缓存 |

目标：**稳定前缀 1.5–2k 字 + 最近 12 轮 + 检索记忆 600–1000 字 + 按需工具**。
这比“换 27B”更能解决“八股/误解”，因为 9B 的注意力预算有限，信息越干净越聪明。

### 3.3 工具调用

- 先只把“纯对话”切本地，工具继续 API（P0）。
- 要本地工具时：
  - 用 3–5 个工具的子集，schema 扁平化；
  - few-shot 2–3 条同格式示例；
  - 输出用 GBNF/JSON schema 约束（llama.cpp grammar）；
  - 解析失败重试 1 次，再降级 API；
  - 评测指标：`tool_call_valid_rate`、`tool_executed_rate`、`empty_content_rate`。

## 4. δ-mem 算法复盘与 v2

### 4.1 现在的算法哪里不稳

论文的 δ-mem 是：冻结全注意力骨干，旁路一个低秩状态 `S`，读 `r=S q`，用 `Δq/Δo` 修正
attention 的 query 和输出。设计前提是：

- 状态是**唯一**的历史来源（训练时 context 从输入里删掉）；
- r 很小（论文 r=8 / d=2560，约 0.31%）；
- 写入按段（SSW），不是按 16 token 硬切；
- 评测是“删掉 context 只留状态”的同分布测试。

你的实现把这四条都改了：

| 论文前提 | 当前实现 | 后果 |
|---|---|---|
| r/d ≈ 0.31% | r=64 / d=4096 ≈ 1.56%（0.6B 上 6.25%） | 修正子空间过大，容易劫持 attention |
| 段级写入 | 固定 16 token | 跨角色/跨句平均，状态混浊 |
| 单次写入训练 | 生产每轮 append | 状态尺度/方向漂移，读到 OOD |
| 同分布评测 | 只测 no-context vs with-state | 看不到生产态退化 |

所以“α×4 有效、α×16 崩、α×1 没记忆”不是调参问题，是**系统在错误分布上标定**。
在这个前提下继续扫 α，只会得到“某个短 prompt 上碰巧能用”的假阳性。

### 4.2 v2 设计：把“无界修正”改成“有界、可关、可查”

核心改动（按优先级）：

1. **零初始化 + 有界残差**
   ```text
   r_t   = RMSNorm(S_{t-1} q_t)
   g_t   = sigmoid(W_g [x_t; r_t; x_t ⊙ r_t] + b_g)      # 每层/每头一个 gate，b_g 初始 -4
   Δq    = g_t ⊙ tanh(W_dq r_t)
   Δo    = g_t ⊙ tanh(W_do r_t)
   q̃    = q + α Δq,   α ∈ [0, 4] 固定或 sigmoid 上限
   ỹ    = y + α Δo
   ```
   - `tanh` 限幅，`g` 近 0 时**严格等于 base**；
   - 加 `L1(g)` 稀疏项，让“无关时不用记忆”成为最优解；
   - `RMSNorm(r)` 防止状态范数漂移导致 Δ 爆炸。

2. **降秩、减层**
   - `r=8–16`，不要 64；
   - 只挂中间层（如 8–23），不要 36 层全挂；
   - 先 N=1，稳定后再试 N=2（事实/风格分开）。

3. **按消息边界写**
   - 训练与推理都传 `boundaries`（每条 user/assistant 消息的 token 长度）；
   - 一条消息一个 chunk，或一个语义段一个 chunk；
   - 对“嗯/哈哈/好呀”这类低信息段，用 salience gate 跳过（或 β 学小）。

4. **顺序写训练**
   - 一条样本 = 一个 session（5–30 轮）；
   - 从空状态开始，逐轮写，写完第 k 轮就在第 k 轮问一次；
   - 每 4–8 轮 detach 一次状态，控制显存；
   - 覆盖 1/5/20/50 次写入后的读取，让模型见过“老状态”。

5. **混合上下文目标**
   - 50% 样本 context 删掉（状态必须扛）；
   - 50% 样本 context 保留（状态只补充）；
   - 其中 20% 是“状态无关/状态过期/状态与 context 冲突”，正确答案是忽略状态或跟 context；
   - 加 `KL(base || steered)` 在通用中文/角色语料上，权重 0.1–0.5，防止把语言建模能力搬进状态。

6. **时间与更新**
   - 写入带 timestamp embedding；
   - 训练“旧事实被新事实覆盖”“上周说的和今天说的冲突，听今天的”；
   - 评测时间衰减，不靠手调 λ。

7. **生产态评测（必须先有）**
   - `Δppl_general`：状态 on/off 在中文通用/角色语料上的 ppl 差，< 2%；
   - `tool_call_valid_rate`：带工具时 100%；
   - `repetition_4gram`：不高于 baseline + 0.05；
   - `empty_rate`：< 1%；
   - `fact_recall@25` ≥ 80%，`preference@25` ≥ 70%，`constraint@25` ≥ 70%；
   - `false_memory_rate` < 5%（状态里没有时不能编）；
   - `conflict_accuracy` ≥ 80%（状态与 context 冲突时跟 context）。

### 4.3 备选方案：memory tokens / retrieval-first

如果 v2 仍然不稳，不要死磕 q/o 注入。两个更稳的方向：

**A. Memory tokens + cross-attention**
- 用一个轻量 compressor 把记忆压成 32–64 个 token；
- 每 4 层加一个 gated cross-attention，让隐状态去读这些 token；
- 参数量小、可解释（能看每个 token 注意谁）、不直接改 q/o；
- 训练数据与 δ-mem 相同；
- 代价：多一层 cross-attention，decode 略慢，但 8B 上可接受。

**B. Retrieval-first（推荐生产先用）**
- 显式记忆库：事件/偏好/约束/关系/时间，带 source、confidence、valid_from/valid_to；
- 检索：BM25 + bge-m3 向量 + 时间衰减 + 实体过滤；
- 注入：5–10 条，按类型分区，600–1000 字；
- 不需要训练，坏了能查，能人工修；
- 缺点：占 context，复杂多跳不如参数化记忆；但对“主链路稳定”是压倒性优势。

**建议顺序**：
1. 生产先上 retrieval-first，δ-mem 关闭；
2. 并行做 δ-mem v2 的数据与评测；
3. v2 在影子模式跑 1–2 周，生产态指标全绿再灰度；
4. 如果 v2 仍不稳，转 memory tokens，不再改 q/o。

## 5. 数据方案（不用你的聊天记录）

### 5.1 明确不用什么

以下一律不进训练集：

- `character/memory/*.txt`（你的原始对话轮次）；
- `logs/log_*.txt`（完整对话日志）；
- `.temp/*_record.txt`（短期记忆）；
- QQ 原始聊天记录、微信记录、私聊截图；
- 任何包含真实 uid、手机号、地址、订单号的文本。

原因不只是“数据差”，还有隐私与合规：一旦这些数据进了 LoRA，权重就是可反推的隐私载体；
自用也有泄漏风险，更不能公开分发。

更关键的是**标签方向错了**：这些记录里 user 侧大量是“问题/抱怨/故障描述”，
assistant 侧大量是 API 的客服腔、过度共情、错误揣测。拿它做 SFT，等于把
“你不想要的行为”当成正样本蒸馏进模型——训得越像，八股和瞎猜越稳。
这不是“数据量不够”，是“正负样本反了”。

### 5.2 δ-mem 数据：从公开多会话 + 合成人设来

**目标**：`(memory_stream, query, response)`，response 只有在读过 memory_stream 时才写得出。

| 来源 | 语言 | 用途 | 量（建议） |
|---|---|---|---|
| PerLTQA | 中文 | 个人长期记忆 QA，最对口 | 3k episodes |
| MSC / Multi-Session Chat | 英文 | 多会话结构；翻译成中文，保留人名/时间/数字 | 3k |
| LoCoMo | 英文 | 与论文对齐；翻译 + 只做评测也可 | 2k |
| NaturalConv / LCCC / 豆瓣 / PTT | 中文 | 语体与多轮结构；改写成 `用户：/我：` | 2k |
| 合成人设 | 中文 | 偏好/约束/关系/项目/宠物/作息；**从角色卡和设定生成，不从聊天记录抽** | 2k |
| 负样本/冲突/更新 | 中文 | “没聊过”“记错了”“以今天为准” | 占 25–30% |

**格式必须逐字复刻生产**（`dmem_bridge.py::_compose`）：

```text
[2026-11-01 20:13]
用户：我今天把混响调好了，但是人声还是有点闷
我：那是高频被压了，先把 8k 提 1.5dB 试试
[2026-11-01 20:15]
用户：对了，下周我可能要去上海
我：去几天？要不要我把日程记下来
```

重建态（`rebuild`）单独一类：

```text
【长期记忆】
- 2026-10-30：主人说下周去上海，三天左右
- 2026-10-28：主人不喜欢香菜
【用户档案】
- 称呼：主人；时区：Asia/Shanghai
```

**样本 schema**（jsonl 一行）：

```json
{
  "id": "ep-000123-q4",
  "episode_id": "ep-000123",
  "owner": "persona-017",
  "language": "zh",
  "sessions": [
    {"time": "2026-11-01T20:13:00+08:00", "turns": [
      {"role": "user", "text": "..."},
      {"role": "assistant", "text": "..."}
    ]}
  ],
  "context": "[2026-11-01 20:13]\n用户：...\n我：...",
  "query": "我下周去哪来着？",
  "response": "上海，三天左右。",
  "segments": [18, 24, 12, 31],
  "memory_type": ["fact", "temporal"],
  "requires_memory": true,
  "memory_absent": false,
  "conflict": false,
  "evidence": ["下周我可能要去上海"],
  "source": "synthetic/persona"
}
```

**质量门（每条都过）**：

1. **实体门**：response 里的实体/数字在 context 出现，且不在 query 里；
2. **判官门**：让 judge 判“删掉 context 还能答吗”，能则丢；
3. **状态门**：训完后算 `no-context NLL − with-state NLL`，≤ 0 的丢掉重训；
4. **上下文门**：保留 context 时，response 不能比 with-state 差太多（否则模型只学会“无视 context”）；
5. **冲突门**：状态与 context 冲突的样本，答案必须跟最新/跟 context；
6. **格式门**：response 不能出现“作为 AI/我理解你的感受/首先其次最后”；
7. **长度门**：response 长度分布要像聊天（10–200 token），不能全是 11 token；
8. **去重门**：按 episode/persona 去重，防同一事实换问法泄漏。

**切分**：按 persona + 时间切，不能按样本随机切。
留出 10% 的 persona 和最后 20% 的 turns；留出集要包含“老状态”“冲突”“无记忆”三类。

**规模**：先 2k episodes / 10k queries 跑通；稳定后 10k episodes / 50k queries。
不要一上来 100k——δ-mem 的参数只有几十 M，数据质量比量重要。

### 5.3 LoRA 数据：中文聊天/角色扮演/工具

**目标行为**：

- 像人说话：短句、口语、停顿、不客服腔；
- 听懂潜台词：反讽、敷衍、“随便”、“你猜”、“我没事”；
- 不胡乱揣测：不确定时问一句，不脑补；
- 角色一致：称呼、口癖、边界、情绪；
- 工具格式：需要时能正确调用，不需要时不乱调。

**来源（按优先级）**：

| 类别 | 数据 | 用法 | 注意 |
|---|---|---|---|
| 中文多轮 | LCCC、NaturalConv、豆瓣、PTT | 语体/节奏；改写为角色对话 | LCCC 研究许可；噪声大，要过滤 |
| 贴吧/论坛 | `chinese-chatbot-corpus` 里的贴吧回帖、PTT、豆瓣 | 网络语体、吐槽、反问 | 帖子不是对话，要构造“楼主→回复→再回复” |
| 角色扮演 | BeyondDialogue、RoleLLM、CharacterGLM、CoSER、CPED | 角色一致、情绪、场景 | 检查许可证；避免 NSFW 混入通用集 |
| 中文 RP 合成 | `shibing624/roleplay-zh-sharegpt-gpt4-data` 等 | 补充多轮 RP | 质量参差，必须 judge |
| 合成 | 用 Qwen3.8-Flash/DeepSeek 从角色卡+场景生成 | 补你的 persona/工具/潜台词 | 不要用你的聊天记录当种子 |
| 工具 | Glaive Function Calling v2、APIBench/BFCL、项目工具 schema | 工具调用 | schema 脱敏，参数用假数据 |
| 通用 | COIG/Belle/Firefly 少量 | 防遗忘 | 不超过 10% |

### 5.3.1 贴吧 / QQ 具体怎么收

**贴吧（可以用，但只当“语体矿”）**

1. 选 20–50 个**话题稳定、回复质量高**的吧（不要选纯水吧/资源吧）；
2. 抓“主题帖 + 前 50 楼回复”，保留：标题、楼层、引用关系、时间、吧名；
3. 构造对话：
   - 楼主主帖 = `user`；
   - 一条有信息量的回复 = `assistant`；
   - 回复里“回楼上/引用的内容”保留引用关系，转成多轮；
4. 过滤：
   - 少于 8 字、纯表情、纯顶帖、广告、对骂、复读 → 删；
   - 含手机号/微信号/二维码/地址 → 删或脱敏；
   - 同一用户连续刷楼 → 只留一条；
5. 用途：
   - **只取语体/反问/吐槽/网络词**，不要把它当“角色对话”；
   - 用 10–20% 混入 SFT，不要超过 30%，否则模型会变得太“贴吧味”；
6. 版权：贴吧内容有版权，自用可以，**不要公开分发用这些数据训出的权重**。

**QQ 群聊（不建议用；除非有明确授权）**

- 即使你有群记录，里面也有别人的隐私；训练进权重后无法撤回；
- 如果一定要用：
  1. 取得群主/成员明确同意；
  2. 删除所有 uid、昵称、手机号、地址、订单、照片、链接；
  3. 按“连续对话段”切 session，去掉机器人/广告/复读；
  4. 只取“语体/节奏”，不要取具体事实；
  5. 训出的 LoRA **不公开、不商用、不跨人使用**；
- 更稳的替代：用贴吧/豆瓣/PTT 的公开语体 + 角色卡合成，效果接近，风险低一个量级。

**潜台词/反八股专用集（建议 1–2k 条，人工+合成）**：

```text
用户：我没事
差的回复：抱抱你，一定很难过吧，我理解你的感受……（八股/过度揣测）
好的回复：嗯。那我不问了，你想说再说。

用户：随便
差的回复：好的，那我们来分析一下有哪些选择……（说教）
好的回复：那我定了，火锅，微辣。

用户：你猜
差的回复：我猜你现在可能有点不开心，因为……（脑补）
好的回复：不猜。你自己说。

用户：今天算了
好的回复：行，那今天先到这儿。明天还这个点？
```

这些样本要进 SFT，也要进 DPO 的 chosen/rejected 对。

**质量过滤（最关键）**：

- 删“作为 AI/我理解你的感受/首先其次最后/希望对你有帮助/如果你愿意可以……”；
- 删列表化、说教、过度共情、心理咨询腔；
- 删“我猜你是……”式无依据揣测；
- 删重复、空话、复述用户；
- 删长度异常（一条回复 500 字以上，除非场景需要）；
- 保留：短句、反问、停顿、口语词、语气词、恰当的沉默；
- 用 judge 打分：自然度、角色一致、潜台词理解、非八股、无幻觉；只留 top 30–50%；
- 去重：MinHash/SimHash，防同一场景刷屏；
- 配比：日常闲聊 40%、情绪/潜台词 25%、角色场景 20%、工具 10%、通用 5%。

**版权**：LCCC/豆瓣/PTT/贴吧都是研究/自用范围；**不要把用这些数据训出的权重公开分发**。
QQ 群聊记录即使公开爬取，也涉及个人信息；不建议用，除非有明确授权 + 匿名化。

### 5.4 LoRA 训练配方（QLoRA）

| 项 | 建议 |
|---|---|
| 基座 | Qwen3.5-9B（中文优先）；Qwen3.8-9B-Distill 做对照 |
| 量化 | 4-bit NF4 + double quant，bf16 compute |
| LoRA | `all-linear`，r=64（数据 5k–15k）；数据更多/风格差异大用 r=128 |
| alpha | `2*r` |
| dropout | 0.05 |
| lr | QLoRA 1e-4；LoRA bf16 2e-4；cosine，warmup 3–5% |
| batch | 有效 batch 16–32（LoRA 对超大 batch 不耐受） |
| seq | 4096（多轮拼接）；packing |
| epochs | 1–2；早停看留出集 |
| 硬件 | 24 GB 4090/A5000 云卡；9B QLoRA seq4096 约 18–22 GB |
| 时间/成本 | 10k 样本 1 epoch 约 3–6 小时；AutoDL 约 ¥10–30/次 |
| 本机 8 GB | 不建议训 9B；可训 4B（seq 2k）但质量有限 |

流程：

1. 数据清洗 → 统一 chat 格式（system/user/assistant，多轮）；
2. SFT（QLoRA）→ 留出集 eval；
3. 可选 DPO/ORPO：chosen=自然/懂潜台词，rejected=八股/误解/过度揣测；
4. 合并 LoRA 到 BF16 → 转 GGUF Q4_K_M/Q5_K_M；
5. 用 llama.cpp 跑 100 条 A/B：base vs LoRA vs API；
6. 通过后再替换生产。

评测：

- 留出集 win rate ≥ 60% vs base；
- 潜台词集准确率 ≥ 70%；
- 八股率（judge）< 10%；
- 工具调用 valid ≥ 98%；
- C-Eval/CMMLU 下降 < 2 分（防遗忘）；
- 4-gram 重复/空回复不高于 base。

|---|---|---|
| 9B 工具调用不稳 | 15 个工具 + 嵌套参数，9B 容易格式错 | 工具子集 + few-shot + grammar + 失败降级 API |
| 8 GB 显存不够 | Windows 桌面 + 16K + Q4 可能只剩 1 GB | 12K/8K context；Q4_K_S；关桌面特效 |
| 长 prompt 退化 | 4.7k 字 system + 40 轮会稀释注意力 | 先压 prompt，再换模型 |
| δ-mem 仍不稳 | 门控/数据都改了也可能不够 | 转 memory tokens 或 retrieval-first，不硬上 |
| LoRA 过拟合/遗忘 | 数据小、风格强 | 1 epoch、r=64、混 5–10% 通用数据、早停 |
| 数据版权 | LCCC/豆瓣/贴吧研究许可 | 自用；不公开分发权重；记录来源 |
| “八股”来自 teacher | 合成数据全是客服腔 | judge 过滤 + DPO 负样本 + 人工抽检 |

**待你拍板的三件事**：

1. 本地模型先接哪几个域？建议 P0 只接 `func/llm`，工具/视觉先留 API。
2. 能否提供 **50–100 条你认为“好”的对话样例**（不是聊天记录，是你手写的理想回复/风格卡）？
   这不会进训练集的“原始记录”，只作为 style rubric；没有也能做，但风格对齐会慢。
3. δ-mem 是继续研究线，还是直接转 retrieval-first？建议后者先上生产，前者并行。

## 9. 一句话总结

**先用 Qwen3.5-9B Q4_K_M + llama.cpp 单流把主对话接住，δ-mem 全部关掉；记忆先用显式检索顶住；
然后用公开中文语料 + 合成角色对话做 QLoRA，把“像人、懂潜台词、不八股”训进去；
δ-mem 只在“按消息边界写、有界门控、顺序写训练、混合上下文、生产态评测”五件事同时做到后再灰度。**
