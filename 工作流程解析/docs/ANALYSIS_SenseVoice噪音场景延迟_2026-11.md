# ANALYSIS：SenseVoice 在"打扫卫生"噪音场景下响应变慢

- 日期：2026-11（数据取自 2026-11-06 15:29–16:27 会话，共 58 分钟，正是打扫卫生那段）
- 数据源：
  - `logs/svc_sensevoice_2026-11-06.log`（服务端识别流水，169 次触发）
  - `scripts/sensevoice_latency/logs/sv_events.log`（毫秒级打点：user_start / user_end / sv_result_sent）
  - `logs/log_2026-11-06.txt`（主程序流水：声纹、LLM 入队、AI 回复、TTS 打断）
- 结论前置：**不是 SenseVoice 变慢，是"噪音把端侧状态机打乱了"**。三个怀疑里，①成立且是主因，③里有一处真实代码缺陷被噪音放大，②不成立。

---

## 一、实测数据

### 1. SenseVoice 本身没有变慢（推翻怀疑 ②）

| 指标 | 值 |
|---|---|
| ASR+声纹 端到端（`user_end` → 结果回传） | n=169，min 241ms，**p50 796ms**，p90 914ms，max 3257ms |
| 3.26s 那条 | 只有一条，是 15:29:53 **首次调用冷启动**（CUDA kernel 预热），之后不再出现 |
| 最长音频 152.4s | 识别只用 2748ms（约 18 倍实时） |
| 按 10 分钟分桶 p50 | 832 / 836 / 756 / 779 / 750 / 728 ms —— **全程无漂移** |
| 传输稳定性 | 0 次重连、0 次会话异常、0 次发送失败、0 次识别失败 |

结论：GPU 侧余量很大（最差也有 18 倍实时），不存在"本地性能受限导致识别不稳定"。服务端 `concurrent_asr=4`、`worker_threads=4` 也没被打满；`inject` 会话虽然也连着，但全程空闲，没有双倍负载。

### 2. LLM 也没变慢（推翻"本地跑不动"的猜测）

| 日期 | LLM 入队 → 回复文本 |
|---|---|
| 11-06（打扫卫生） | n=47，p50 **5.62s**，p90 6.62s |
| 11-03（正常使用） | n=90，p50 **5.82s**，p90 10.73s |

同一口径下 11-06 反而略快。且模型是云端（`deepseek` / `aliyun` 兼容接口，`stream=true`），本来就不吃本地算力。

### 3. 单轮固定开销 ≈ 9.4s，这才是"慢"的账面来源

```
2.0s   静音确认   silence_threshold=2.0     ← 说完话后必须连续 2s 低于 vad_energy_threshold 才上报"说完了"
0.8s   ASR+声纹   （实测 p50）
1.0s   merge_delay=1.0                      ← 收到 final 后再等 1s 收集下一句
5.6s   LLM 首句
--------
9.4s 才开口（还没算 TTS 首帧）
```

用户原话（15:32:59 那段识别结果）："之前稳定 5 秒钟给我反馈，你现在起码 10 秒钟有吗？" —— 和 9.4s 的账面值完全吻合。

## 二、噪音是怎么把这个 9.4s 放大到 20～30s 甚至"完全不回"的

### 链路 A：单帧噪音就能重置断句计时器（放大器 #1）

`func/sensevoice/interrupt.py::_update_speaking`：

```python
if is_speech:                      # energy >= 300
    self._silence_start_time = None    # ← 只要有一帧(30ms)超过 300，2s 倒计时整个清零
```

不是"累计静音 2s"，而是"连续 2s 一帧都不能超"。打扫卫生的塑料袋、拖凳子、脚步声，每隔一两秒就来一下 → **倒计时永远走不完** → 一句话关不上。

实测后果：

- 音频段长度 p50 6.0s、p90 23.7s、**max 152.4s**，≥30s 的有 6 段；
- 说"该切句"的地方不切，用户连说三句被攒成一段。

### 链路 B：每来一次噪音 = 一次 `start` 事件 = 三件事同时被打断（放大器 #2）

`_vad_tick` 里 `vad_event == 'started'` 时同时做：

1. `manager.on_speech_start()` → **取消 merge 计时器**
2. `_abort_answer()` → **当前 LLM 生成立刻收手**（`[打断] 用户开口`）
3. `tts_bridge.set_speaking(True)` → **停掉正在播的语音**（`_interrupt_playback` 会清空整个回答队列 + generation++）

本轮会话实测：

| 事件 | 次数 |
|---|---|
| `检测到用户开始说话，打断 AI 语音` | **170**（= 169 次 ASR 触发，几乎一一对应） |
| `[打断] 用户开口，当前生成收手` | **169** |
| LLM 入队 50 次 → 真正产出回复 | **只有 29 次**；**21 次（42%）被中途掐掉，一句话都没说出来** |
| TTS 被压制时长 | p50 5.0s，p90 **23.1s**，max **72.6s** |

用户当时在日志里连着问的"不是为什么没有声音啊？""小猫怎么不说话""是不是你话筒那头又没上来" —— 对应的就是这 170 次误打断。**不是漏识别，是回答被噪音掐死了。**

### 链路 C：merge 计时器可能永远不再启动（这是一处真实代码缺陷）

`func/sensevoice/manager.py`：

```python
# on_speech_end() 只是打标记
self._expecting_final = True

# _handle_result() 里：声纹失败的早退发生在打标记之前
if not self.speaker_allowed(...): return          # ← 直接 return
if spk_score < self.config.speaker_threshold: return
...
if self._expecting_final:
    self._expecting_final = False
    self._start_merge(key)                        # ← 只有"被接受的 final"才会重启计时
```

时序：

1. 真话说完 → VAD stop → `_expecting_final=True` → 结果回来 → merge 开始睡 1s；
2. 塑料袋响一下 → VAD start → **merge 被取消**，`_expecting_final=False`，但 `pending_texts` 里的那句话**留在原地**；
3. VAD stop → 这段噪音的识别结果回来，声纹判 `unknown` → `_handle_result` 早退 → **没有重启 merge**；
4. → 那句话就一直扣在 `pending_texts` 里，**直到下一次"被声纹接受"的句子到来才一起发出去**。

实测被扣住的例子：

| 时间 | 现象 |
|---|---|
| 16:01:39 识别到"袜子还乱往地上扔…" | 16:02:08 才送进 LLM，**扣了 29.0s** |
| 16:17:33 识别到"这回复延迟好大呀…本地跑的问题" | 16:17:48 才送进 LLM，**扣了 13.9s** |
| 15:35:01 / 15:35:07 / 15:35:28 三句 | 合并成一条 15:35:29 才发，首句等了 **28s** |

### 链路 D：噪音把声纹打分拉低，38% 的真话被直接丢弃（放大器 #3）

| 指标 | 值 |
|---|---|
| 169 条识别结果中被拒 | 92 条（54%） |
| 只看**有效句**（≥4 字）120 条 | **45 条被判 `unknown` = 38%** |
| 通过声纹的 75 条中，分数 <0.30（贴 0.2 阈值过线） | 34 条（**45%**） |
| 通过声纹分数 p50 / min / max | 0.308 / 0.205 / 0.431 |

被误杀的都是明显能用的真话，例如：

- "那东西好多。"
- "一个来小时先完的上了再说。"
- "哎，确实啊语音识别跑本地也有点压力。"
- "让我发消息的那个群。"
- "红方一街。"
- "还是你收拾会。"

机理：CAM++ 声纹 embedding 提取的是**整段音频**，噪音混进去后 embedding 被污染；而这段音频还带着 2s 的静音尾巴 + 噪音尾巴，进一步稀释。干净场景分数普遍 0.35~0.45，噪音里掉到 0.20~0.25，正压在 `speaker_threshold=0.2` 这条线上。这一条同时反向喂给链路 C（被拒 → merge 不重启 → 后面的真话继续被扣）。

### 链路 E：25% 的 ASR 调用是纯噪音

- 42/169（**25%**）的识别结果是 `[unknown] .` / `。` / `Yeah.` 这类空壳；
- 这些段的音频长度最小 2.4s（= 0.4s 噪音 + 2.0s 静音尾巴），中位 2.7s；
- 单次只花 ~0.74s GPU，**算力上完全不心疼**，但它们每一次都会触发链路 B 的三连打断。

## 三、三个怀疑逐条判定

| 怀疑 | 判定 | 依据 |
|---|---|---|
| ① 生活化噪音大，需要改配置适配 | **成立，主因** | `vad_energy_threshold=300` 太低 → 单帧噪音重置 2s 倒计时；`interrupt_threshold=500` 太低 → 170 次误打断、TTS 被压制 p90 23s / max 72.6s |
| ② SenseVoice 识别变慢、本地性能受限 | **不成立** | ASR p50 796ms 全程无漂移，最差 18 倍实时；唯一 3.26s 是首次冷启动；LLM 5.62s 与 11-03 的 5.82s 持平且走云端 |
| ③ 其它代码 bug / 声音传递不稳 | **部分成立** | 传输侧干净（0 重连/0 异常）；但 `manager._expecting_final` 与"声纹早退"的组合会让 merge 计时器永久停摆，造成 14～29s 的无声扣留——这是真 bug，被噪音触发 |

**一句话：感知到的"慢"= 2s 断句确认 + 1s merge + 0.8s ASR + 5.6s LLM ≈ 9.4s 的底噪，再被噪音引起的①断句失败 ②回答被掐 ③声纹误杀 ④merge 停摆放大到 20～30s，并且有 42% 的回答根本没出声。**

## 四、只改配置能拿到的改善（不动代码）

> 注：无法从日志反推现场噪音的 RMS 绝对值，下面的数值是方向性建议，改完应实机听一遍再微调。

| 配置项 | 现值 | 建议 | 作用 / 风险 |
|---|---|---|---|
| `sensevoice.vad_energy_threshold` | 300 | **600～800** | 让塑料袋/脚步不再算"说话"，2s 静音倒计时才能数得完。风险：小声/远离麦克风可能漏，需实机确认 |
| `sensevoice.interrupt_threshold` | 500 | **1200～1500** | 最高性价比的一条：只有真说话音量才打断 TTS，170 次误掐主要是它造成的 |
| `sensevoice.silence_threshold` | 2.0 | **1.2～1.5** | 直接砍掉 0.5～0.8s 固定延迟。风险：配合抬高后的 vad 阈值才安全，否则会切碎句子 |
| `sensevoice.merge_delay` | 1.0 | **0.4～0.6** | 直接省 0.4～0.6s。句子已经靠 VAD 合并，1s 太保守 |
| `sensevoice.speaker_threshold` | 0.2 | **0.15**（或保持 0.2 但先解决噪音） | 恢复一部分 38% 的误杀。风险：他人误入概率上升；`target_speakers` 白名单仍在兜底 |

配合关系很重要：**光降 `silence_threshold` 不抬 `vad_energy_threshold` 会更碎**（噪音本来就在反复重置倒计时），所以这两条要一起动。

## 五、要根治必须动代码的点（本次不改，仅记录）

1. **`interrupt.py` 断句改成"计数式"而非"清零式"**：连续 N 帧（如 60% 以上帧）低于阈值才判停，或允许 100～200ms 的噪音尖峰不重置倒计时。这是链路 A 的正解。
2. **打断判定与 VAD 解耦**：`update_interrupt` 也要求持续 ≥150～250ms 才置位，单帧不触发。这是链路 B 的正解。
3. **`manager._handle_result` 的声纹早退不能跳过 merge 状态机**：被拒的结果也要 `_expecting_final` 检查/重启计时；或者给 `pending_texts` 加一个"最大累积时长"（如 8s）强制 flush。这是链路 C 的正解。
4. **声纹打分前裁掉首尾噪音**：对整段音频做一次能量门限裁剪再送 CAM++，可把"噪音污染 embedding"的误杀压下去。
5. **空壳结果（`.`/`。`/单字符）应在进状态机之前就丢掉**，目前是靠声纹拒绝兜底，副作用是它会把 merge 计时器拖死。
