# PLAN：用"回译"去 AI 味 —— 可行性评估与落地路线

- 状态：草案（未改任何代码）
- 日期：2026-11-07
- 范围：LLM 回复输出链路（`func/llm/output.py`）+ 水词清洗（`func/llm/narration/`）
- 结论先行：**方向成立，但"把翻译塞进水词算法"不是好形态；回译更适合当"探针 + 词库挖掘机 + 可选兜底"，而不是主链路去味器。**

---

## 0. 一句话结论

1. 论文证明的是：LLM 原文相对"回译文本"显著更多地使用与理解难度相关的特征；回译把文本拉回**高频、常规、低标记**的分布。这支持"回译能削掉模型特有的、反常规的句法"。
2. 论文**没有**证明回译文本更"通俗"、更"像人"、更适合中文聊天或角色扮演；也没做人因实验。"更难懂"是用心理语言学特征做的代理测量。
3. 回译的代价是**去风格化 + 翻译腔**。论文自己引用翻译研究：翻译会降低词汇/句法丰富度、剥离风格与作者特征（§3.4）。对角色扮演 bot，这是双刃剑。
4. 所以：回译值得做，但建议按 **P0 影子探针 → P1 离线 A/B → P2 词库挖掘 → P3 在线受控改写** 走，先让数据说话。
5. 直接回答你的问题：**"优化水词算法来做翻译"不是很好的方案；"把回译作为独立一层，先用它反向优化水词算法"是很好的方案。**

## 1. 论文速读（只摘和本方案相关的）

### 1.1 基本信息

- 标题：*Why is AI-generated language so hard to understand?*
- 作者：Thomas Hikaru Clark（NYU）、Matias B. Martin、Kyle Mahowald（UT Austin）
- arXiv:2610.29162v1 [cs.CL]，2026-10-21，23 页

### 1.2 方法

- **语料**：14 个模型（9 个 frontier/near-frontier + 5 个小开源模型）× 三个场景：多轮 chat（10 话题 × 12 模型）、coding（5 仓库 × 9 模型）、PERSUADE 议论文（7 题 × 14 模型）。对照组是人写文本（OpenSubtitles / StackExchange / 学生作文）。
- **特征**（全部来自 spaCy 依存句法）：
  - 宾语关系从句（带/不带关系词）
  - 去名词化动词（denominal verbs，如 *calendar it*）
  - 无灵主语 + 通常只接有灵主语的动词（如 *the conversation is eating its tail*）
  - 依存距离
  - 名词堆叠（三个及以上名词作修饰）
  - 未登录 n-gram / n-gram 困惑度
- **回译**：NLLB-200（3.3B），**逐句独立**做 English → Japanese → English；选日语枢轴是因为"与英语无关的枢轴语言能产生更多样的复述"（Federmann et al., 2019）。回译句与原句配对，语义受控。
- **注意**：回译在论文里的身份是 **measurement instrument（测量工具/控制变量）**，用来把"模型输出的句法特征"从"语义内容"里分离出来——不是被验证的"治疗方案"。

### 1.3 主要发现

- frontier/near-frontier 模型在 chat/coding 中显著**过度使用**上述难懂特征；议论文场景效应较小；Llama、Olmo base 基本没有，Olmo Think 又变大。
- 回译后这些特征显著下降（Figure 3 / Figure 6）。典型句子：

  > "Your instinct is right; the convoluted sentence you are currently reading is quietly eating its own reader-patience budget — footnote it."

  这句话同时叠了宾语关系从句、去名词化动词、无灵主语、名词堆叠、低频 n-gram——回译会把它压平。
- 解释（H2）：后训练（RLVR、面向数学/代码的奖励）带来**信息密度压力**，与"让人好懂"的目标竞争；作者用 GRPO + 长度惩罚做 proof-of-concept，模型确实学会了选更短的可选结构，甚至泛化到训练中没见过的句法交替。
- 所以论文的"药方"在**训练侧**（奖励/惩罚设计），不在推理侧。

### 1.4 关键限定（很重要，别过度引用）

- **没做人类可理解性实验**：全文用心理语言学特征做代理，没有让真人读回译文本打分。
- **只有英文**，只有 NLLB，只有日语/俄语枢轴；中文、QQ 聊天、角色人设均未验证。
- **回译不是单向"变简单"**：Figure 3 里存在 "round trip higher" 的格子（例如带关系词的关系从句，模型本来就用得少，回译反而更多）。中文里的对应现象是：显化主语、代词增多、"的"字链变长、语序变僵——即**翻译腔**。
- **逐句翻译会打断句间连贯**：指代、省略、话题链在句子边界被切断；论文报告 2.4%（NLLB 日枢轴）到 14.1%（TranslateGemma 日枢轴）的句子回译后变成多句（即句子被拆开）。
- **翻译会去风格**：对人设角色，口癖、称呼、语气词、网络梗都可能被"规范化"掉。
- **回译治不了"内容层"的 AI 味**：空洞大词、强行升华、正确的废话，翻译只会把它们译得更通顺，不会让它们变得有内容。

## 2. 现有水词算法：它擅长什么、不擅长什么

### 2.1 机制（对照代码）

- 词表：`adjunct_word.json`（可删除，类别 1–5）+ `score_only_word.json`（只计分不删，保护人设词如"喵"）。
- 结构：Trie 前缀树，最长匹配优先；`NarrationCore` 维护 EWMA 平滑分 `S`，按 `part_level_upper/lower` 映射到三档：
  - `LEVEL_FULL`：不删（分数高，说明上轮够"干净"）
  - `LEVEL_PART`：只删类别 2/3/5（口癖、过渡词、套话）
  - `LEVEL_ALL`：删所有可删除词
- 清洗器 `NarrationCleaner` 是**逐字符流式**的：`feed(ch)` 边生成边删，`flush()` 收尾。
- 打分 `_raw_score`：`density = 100 − W/L×100`，W/L 超阈值直接 0；再按超长做惩罚；`update()` 用**清洗前的原文** `filtered_content` 做 EWMA。
- 集成点：`Output.finalize()` 末尾调用 `narration.update(self.filtered_content)`；TTS 分段是流式的（`_split_send`）。

### 2.2 强项

- 确定性、可解释、零额外延迟（纯本地字符串处理）。
- 词级精准；词表可热更新；`score_only` 能保护人设词。
- 已经有"按上一轮表现动态调档"的反馈机制，和"越说越水就删得越狠"的直觉一致。

### 2.3 盲区

- **只能删，不能改**。删多了会断气："我觉得其实吧这个方案……"删成"这个方案……"，信息没丢但语气没了。
- **抓不到句法级 AI 味**：长句、多层定语、名词堆叠、无灵主语、排比、三段式、"首先/其次/最后"、破折号。
- **抓不到内容层 AI 味**：空洞大词、过度总结、强行升华、正确的废话。
- **EWMA 是反馈回路**：任何"先改写、再打分"的做法都会污染反馈（回译会把分数抬高 → 档位下降 → 清洗变弱 → 下一轮更水）。必须隔离。

### 2.4 结论

水词层是**词级删除**，回译层是**句法级重写**。两者是互补关系，不是替代关系；合并会同时失去"确定性"和"保真度"。

## 3. 方案判断

### 3.1 不推荐的三种形态

| 形态 | 为什么不推荐 |
|---|---|
| A. 把翻译逻辑写进 Trie/cleaner | 粒度冲突：逐字符流式 vs 整句批处理；失败模式完全不同 |
| B. 用回译替代水词删除 | 丢确定性、增延迟、可能引入翻译腔；删词变改写，不可解释 |
| C. 每条回复实时全量回译 | 延迟 + 成本 + 人设风险；QQ 聊天节奏扛不住（见 §5.5） |

### 3.2 推荐的形态：三层管线

```
模型原始输出
   │
   ├─ L0 词级：现有水词删除（流式，保留）
   │
   ├─ L1 句法级：回译/约束改写（可选、门控、句级、超时回退）
   │
   └─ L2 语用级：人设/格式/长度守护（校验与回退）
   │
   ├─ EWMA 打分：只用"模型原始输出"，不用改写结果 ← 隔离反馈
   └─ 改写后分数：单独记录，仅用于监控
```

- **计分隔离**是硬要求：`update()` 继续吃 `filtered_content`；回译结果另算一份 `rewrite_score` 写日志，不回灌 `S`。
- **顺序**：生成 → 句级改写（可选）→ 水词清洗 → 标点整理 → TTS/发送。改写后仍要过 cleaner，因为回译可能带回套话。

### 3.3 回译的三种正确用法（按性价比排序）

1. **离线探针（P0）**：对历史回复做回译，算特征 delta，给每条回复一个"回译可改善度"。零线上风险，直接回答"到底值不值得做"。
2. **词库挖掘（P2）**：`original − round-trip` 差分，消失的 n-gram/短语 → 候选水词，人工审核进 `adjunct_word.json`。这是对现有算法最直接的优化，且不需要改运行时。
3. **在线兜底归一化（P3）**：只对"AI 味高 + 无人设词 + 无俚语/格式"的句子做回译，超时/失败回退原文。

## 4. 如果要上线：目标架构

### 4.1 插入点

- **句子级缓冲**，不是字符级。以 `。！？!?…` 和 `split_limit` 为边界；一句攒够就送去改写。
- 改写结果回填到 `Output` 的 `temp`/发送队列，**不改变现有分段语义**（段序号、TTS 队列、chat_status 都保持）。
- 若走 TTS：改写后的句子仍需 `_collapse_punctuation`/`_clean_punctuation`。

### 4.2 竞速与超时

- 改写线程与 TTS/发送"竞速"：句子到达后启动改写，**超时 300–500ms** 未返回就直接用原文。
- 这样最坏情况只损失"这一句没改写"，不会拖垮整条回复。
- 禁止同步阻塞整段回复；禁止在 `feed()` 里做网络调用。

### 4.3 开关与灰度

- `config.yml` 增加独立开关（不建议塞进 `llm.narration`，避免和现有档位逻辑耦合）。
- 支持按群/按角色灰度；支持"影子模式"（只记录，不改变输出）。
- 一键回滚：关开关即回到现网行为。

### 4.4 与现有 `narration` 的关系

- `NarrationCore` 不感知改写器；改写器是 `Output` 之外的独立组件。
- `current_level()` 仍然按 `S` 决定"要不要触发改写"；改写器不反向修改 `S`。
- 词表挖掘产出的新词，仍走 `adjunct_word.json` 的类别体系（2/3/5 或新增类）。

## 5. 关键设计细节

### 5.1 门控：什么时候值得改写

同时满足才触发（建议初始值，可调）：

- 本轮 `current_level()` 为 `PART` 或 `ALL`（说明上一轮偏水/偏长）；
- 句子长度 ≥ 12 字（太短没有改写空间）；
- 句子水词密度 ≥ 阈值，或命中"结构套话"规则（见 §5.4）；
- 不含保护内容：URL、@、代码块/行内代码、emoji、颜文字、数字串、引号内引用；
- 俚语/梗密度低（维护一个小词表，命中即跳过）；
- 非命令/非工具输出/非系统消息。

再加**概率抽样**（如 0.3）：即使满足条件也只改一部分，避免"每句话都被洗一遍"的塑料感，也控制成本。

### 5.2 翻译器与枢轴选型

| 方案 | 模型/服务 | 枢轴 | 质量 | 延迟（CPU） | 成本 | 备注 |
|---|---|---|---|---|---|---|
| A | NLLB-200-distilled-600M（CTranslate2 int8） | zh→en→zh | 中 | ~0.2–0.5s/方向/句 | 本地 | 权重约 1.2GB(fp16)/2.4GB(fp32)；license CC-BY-NC 4.0 |
| B | opus-mt-zh-en + opus-mt-en-zh（Marian） | zh→en→zh | 中低 | ~50–150ms/方向/句 | 本地 | 两个 ~300MB；Apache-2.0，许可最稳 |
| C | LLM 约束重写（不翻译） | — | 高（能保人设） | 0.5–2s/次 | 高 | 可能带回同族 AI 味；需强提示词 |
| D | API MT（DeepL/Google/百度） | zh→en→zh | 中高 | 100–300ms/次 | 按量 | 零部署；隐私与网络依赖 |
| E | 回译 + LLM 重写混合 | zh→en→zh，再让 LLM 校 | — | 最慢 | 最高 | 仅 P3 实验 |

- **枢轴**：`zh→en→zh` 最稳；`zh→ja→zh` 复述更多样，但中文俚语/梗容易译坏；`zh→ru→zh` 不推荐。
- **建议**：P1 先测 A/B 两种本地方案（成本低、可离线批量），P3 再评估 C。
- **许可提醒**：NLLB 是 CC-BY-NC，商用需确认；opus-mt 是 Apache-2.0。

### 5.3 保护与校验

| 项 | 做法 | 失败处理 |
|---|---|---|
| 格式保护 | URL/@/代码/emoji/数字/引号内容 → 占位符，改写后还原 | 还原失败 → 回退原文 |
| 人设保护 | 维护保护词表（口癖、称呼、角色名、专属语气词），改写后校验保留 | 缺失 → 回退或回填 |
| 语义校验 | embedding cosine（bge-small-zh/text2vec）≥ 0.90–0.92；或 NLI entailment | 不达标 → 回退 |
| 长度校验 | `0.7 ≤ len(out)/len(in) ≤ 1.4`；句数变化 ≤ 1 | 越界 → 回退 |
| 超时 | 300–500ms/句 | 超时 → 原文 |
| 缓存 | `hash(句子 + 模型 + 枢轴 + 版本)` → 结果；QQ 场景重复率高 | 命中直接用 |
| 禁用场景 | 代码、链接、@、整活/梗、命令、敏感内容 | 跳过 |

### 5.4 中文"AI 味"评分卡（把论文特征映射过来）

论文的英文特征不能直接套中文；下面是"同构替换"：

| 维度 | 论文特征 | 中文可操作指标 | 检测方式 |
|---|---|---|---|
| 词汇罕见度 | unattested n-grams / perplexity | 低频搭配率、生造词、"进行/加以/予以 + 名词"弱动词结构 | 中文 n-gram 频率表 + 小 LM 困惑度 |
| 名词堆叠 | stacked nouns | "的"字定语链长度、四字格连用 | 依存句法（HanLP/LTP）+ 规则 |
| 无灵主语 | inanimate subject + animate verb | "这句话在吃掉你的耐心"类物化/拟人 | 规则 + 小分类器 |
| 依存距离 | dependency length | 平均依存距离、跨句指代 | HanLP/LTP |
| 结构套话 | — | "首先/其次/最后""不是…而是…""值得注意的是""总的来说"、破折号、排比 | 规则 + 现有水词库 |
| 篇章 | — | 总分总、总结词位置、升华句 | 规则 + 位置特征 |
| 语用 | — | 句长分布、emoji、语气词、反问比例 | 统计 |
| 翻译腔（回译副作用） | translationese | 主语显化、代词增多、"的"字变多、语序僵化 | 与原创中文聊天语料对比 |

> 说明：论文的 "denominal verbs"（去名词化动词）在中文里对应较弱，可近似用"弱动词 + 名词"结构替代；"reduced ORC"在中文没有直接对应，跳过。

### 5.5 成本/延迟粗算

- 一句 20–40 字，NLLB-600M int8 CPU：每方向 0.2–0.5s → 每句 0.4–1s；5 句回复串行 **2–5s**。GPU 可降到 ~50–100ms/句。
- opus-mt：每方向 50–150ms → 每句 0.1–0.3s，5 句 **0.5–1.5s**。
- LLM 重写：每次 0.5–2s + token 成本。
- **结论**：在线全量回译不现实；必须"句级 + 竞速 + 抽样 + 缓存"。P0/P1 离线批量则无所谓。

## 6. P0：影子探针（建议先做这个，不改任何输出）

### 6.1 做什么

- 采样历史回复（脱敏，去掉昵称/群号/链接），对每条做 `zh→en→zh` 回译；
- 计算：
  - 评分卡各项 delta（§5.4）；
  - 词级差集：原文有、回译没有的 n-gram/短语（候选水词），以及反向新增（翻译腔候选）；
  - 语义 cosine、长度比、句数变化。
- **只写日志/报表**：不改回复、不改打分、不改 TTS。

### 6.2 产出

- 每条回复的"回译可改善度"分布：多少回复几乎没差（→ 回译没必要），多少差很大（→ 候选）；
- 新水词候选 top N（按消失率排序）；
- 与现有 EWMA `Raw` 的相关性：现有打分是否已经抓住了回译能抓的东西。

### 6.3 决策标准

- 若 ≥30% 的回复在评分卡上显著改善，且语义/人设损失可控 → 进 P1；
- 若改善只集中在少数句式、且水词层已覆盖 → 停，转 P2 词库挖掘即可；
- 若"回译新增特征"（翻译腔）比例高 → 直接放弃在线回译。

## 7. P1：离线 A/B

- **数据**：300–500 条真实回复（覆盖聊天/工具/情绪场景）+ 100 条人写对照（同人设、同话题），3 名标注者盲评。
- **分组**：
  - A 原文
  - B 水词 only（现网）
  - C 水词 + 回译（zh-en-zh）
  - D 水词 + 回译（zh-ja-zh）
  - E 水词 + LLM 约束重写（"降低信息密度"提示词，见下）
- **指标**：自然度、人设一致、信息保真（1–5 分）；评分卡；语义 cosine；长度；延迟；成本；"有趣度"（防止过度归一化变平庸）。
- **建议通过线**（可调）：
  - 自然度 ≥ B + 0.4（5 分制）
  - 人设一致 ≥ 4.0，保护词保留 100%
  - 语义 cosine ≥ 0.92
  - 评分卡改善 ≥ 20%
  - p95 延迟增量 ≤ 400ms（异步/竞速下）
  - 成本 ≤ 现网 +10%
- **E 组提示词方向**（论文机制的直译）：
  - "把这句话改写成更低信息密度、更口语的说法：拆长句、少用名词堆叠、补必要的虚词、保留人设词与事实；不要新增信息，不要升华。"
  - 这比"翻译再翻回来"更可控，也更保人设；回译可以视为它的廉价代理。

---

## 8. P2：把回译变成"水词挖掘机"（低风险，建议先做）

- 对历史回复批量回译，diff 出"原文有、回译没有"的 n-gram/短语；
- 过滤停用词、人名、剧情词、专有名词；
- 按消失率排序，人工审核 → 加入 `adjunct_word.json` 对应类别（2/3/5 或新增类）；
- 同时用回译 delta 作为"AI 味"外部标签，评估现有 `Raw` 分的区分度（AUC）：
  - 如果 `Raw` 和回译 delta 高度相关 → 现有算法已经够用，回译只做离线；
  - 如果相关性低 → 说明 `Raw` 漏掉了句法级 AI 味，值得做在线层。
- 这条路**不改运行时链路**，直接增强现有算法，也最符合"优化水词算法"的原意。

---

## 9. P3：在线受控改写（可选，最后做）

- 只在 P0/P1 证明有净收益时做；
- 句级 + 竞速 + 抽样 + 门控 + 回退（§4、§5）；
- 先灰度一个群/一个角色，观察 1–2 周：回复长度、被 @ 率、用户反馈、TTS 时长、异常日志；
- 保留"一键关闭"。

## 10. 风险清单

| 风险 | 表现 | 缓解 |
|---|---|---|
| 人设稀释 | 口癖/称呼/语气消失 | 保护词、校验、回退、只改句法不改词 |
| 翻译腔 | "的"多、主语显化、语序僵 | 评分卡监控；opus/NLLB 对比；限制改写幅度 |
| 语义漂移 | 梗/俚语/双关被译坏 | 俚语检测跳过；语义 cosine 门槛；缓存人工抽检 |
| 内容层 AI 味没治 | 空洞大词、强行升华 | 不指望回译；用提示词/人设约束/内容策略 |
| 延迟 | 首字延迟增加 | 句级竞速、超时回退、抽样、GPU |
| 成本 | MT 调用/显存 | 缓存、抽样、本地小模型 |
| 反馈震荡 | EWMA 被改写结果污染 | 打分只用原始输出；改写结果单独监控 |
| 格式破坏 | URL/@/代码/表情 | 占位符 + 还原 + 禁用场景 |
| 许可 | NLLB CC-BY-NC | 确认项目用途；opus-mt Apache-2.0 更稳 |
| 过度归一化 | 文本变平庸、失去个性 | 限制幅度、保留人设词、人工评估"有趣度" |

## 11. 待你拍板

1. **目标优先级**：是"更像人/更自然"，还是"更短/更少水词"，还是"更像某个角色"？三者最优解不同。
2. **部署形态**：能接受本地跑一个 600M MT 模型（显存/CPU/依赖），还是只接受 API 或 LLM 重写？
3. **先做哪条**：建议 P0 影子探针 + P2 词库挖掘并行（都不改线上行为），P1 用离线数据，P3 最后。

## 附：一句话回答你的问题

"用回译去 AI 味"方向成立，但它是**句法归一化**，不是**通俗化**；把它做成独立的一层、先用它当探针和词库挖掘机，比改造水词算法更划算。等 P0/P1 的数据说话，再决定要不要进主链路。

> 如果你说的"语音"是指 TTS/ASR 链路：论文不涉及音频；不要做"ASR → 翻译 → 再合成"的回译，误差会叠加，且失去文本可校验性。文本回译才是论文的方法。
