# ANALYSIS：NapCat 掉线诊断 &「整合包 + 低风控」可行性（2026-10）

> 本文只做诊断与方案分析，**未改动任何代码/配置**。
> 证据分三档：**强**（本机日志/文件实测）、**中**（官方文档/社区共识）、**弱**（推断，需实测确认）。

---

## 一、现状：这条链路到底是怎么跑的（强证据）

### 1.1 启动链路（从日志与文件还原）

```
GUI 启动球
  → POST /api/start_napcat              (api.py / config_gui.py)
  → gui/tools/launcher.py  SERVICES['napcat']  kind=bat
  → .vendor/.NapCat/NapCat.Shell/napcat.quick.bat
  → NapCatWinBootMain.exe 10086
  → 注入 NapCatWinBootHook.dll 到 .vendor/.NapCat/NapCat.Shell/QQ.exe
  → QQ.exe 读 versions/config.json，装载 versions/9.9.26-44498/QQNT.dll
  → resources/app/package.json 的 main 被换成 ./napcat/napcat.mjs
     （原文件保留为 package.json.bak）
  → napcat.mjs 用 QQ 的 wrapper.node 起主进程，挂钩 native 收发
     （napcat.json: packetBackend=auto, o3HookMode=1）
  → OneBot v11 正向 WS  127.0.0.1:3001
Python 侧 ← TBNapCatConnection（websockets，固定 3 秒重连）
```

一句话：**不是"无头协议端"，是"官方 QQNT + 注入 + 换掉 QQ 自己的 JS 主进程"**。

### 1.2 关键事实表

| 事实 | 证据 | 档位 |
|---|---|---|
| QQ 本体在整合包内 | `.vendor/.NapCat/NapCat.Shell/versions/9.9.26-44498/QQNT.dll`（206 MB） | 强 |
| **账号数据不在包内** | 日志：`本账号数据/缓存目录：D:\QQ\files\TencentFiles\Tencent Files\NapCat\data`；且 `D:\QQ\...\3781465760\nt_qq\nt_db\nt_msg.db` 在 10-28 12:07 仍被写入 | 强 |
| 快速登录 100% 失败 | `napcat.quick.bat` 写死 `NapCatWinBootMain.exe 10086`；每次启动都有 `快速登录失败，未找到该 QQ 历史登录记录` | 强 |
| 掉线只写日志，不处理 | `[KickedOffLine] [下线通知] 你的账号当前登录已失效，请重新登录。` 之后只有 `账号状态变更为离线` | 强 |
| 掉线很频繁 | 10-18×2、10-19×1、10-21×2、10-22×11、10-23×3、10-28×2，共 21 次 | 强 |
| 没有自动恢复 | `connection.py` 只有 `except → sleep(3)`；无进程拉起、无登录态探活、无告警 | 强 |
| 客户端版本低于本机 QQ | 包内 `9.9.26-44498`；本机安装 `9.9.29-47354`（HKLM `...\Uninstall\QQ`） | 强 |
| 配置写在版本目录里 | `versions/9.9.26-44498/resources/app/napcat/config/napcat_<uin>.json` | 强 |
| 无窗口运行 | `launcher.py` 统一 `CREATE_NO_WINDOW`；`napcat_setup.py` 的目的是让它在无窗口下也能看日志 | 强 |

### 1.3 三个由此推出的结论（弱→中）

1. **"整合包"目前是半整合**：QQ 二进制随包，登录态跟着宿主机（`D:\QQ`）。换台机器 = 无历史登录记录 = 必须重新扫码；这既破坏"开箱即用"，也放大了风控面。
2. **每次启动都是一次全新登录**：`-q 10086` 这个占位号让"快速登录"永远不可能命中真实账号（3781465760），于是每次都走扫码。10-28 一天就登了 3 次（00:02 / 10:56 / 12:07）。
3. **掉线后系统是"静默"的**：NapCat 进程还活着、WS 还连着，Python 侧只会在真正断 WS 时每 3 秒刷 `远程计算机拒绝网络连接`。所以实际表现是"看起来在线，其实发不出去"。

## 二、把「无头 QQ 会封号」这句话校准

网络上这句话把三种完全不同的东西混在一起：

| 类别 | 代表 | 底子 | 风险来源 |
|---|---|---|---|
| 纯协议重实现 | Lagrange.Core、icqq、go-cqhttp 的 NT 分支 | 自己实现 NTQQ 协议 | **最高**：没有真实客户端、没有官方上报/签名链路 |
| **真客户端 + 注入** | NapCat、SnowLuma、LLOneBot | 官方 QQ.exe | 中：客户端被改动、组件不完整、行为异常 |
| 官方 bot | QQ 开放平台 | 官方服务端 | 合规，但拿不到"私人陪聊/群聊插话"这种自由度 |

本项目属于第二类。所以真正的问题不是"要不要无头"，而是：

> **这台机器上跑的那个 QQ，在腾讯眼里是不是"一直就是同一台机器上那个正常的 QQ"。**

社区/官方文档里能对上的经验（中证据）：

- NapCat [安全文档](https://doc.napneko.icu/other/security)：避免同一 IP/设备上同时登录 bot 号与常用号；掉线频繁可通过换账号/换设备改善；可把 `o3Hook` 设为 0 关闭包拦截；网络复杂时用 SOCKS5 代理。
- 社区帖（[locdd 44114](https://www.locdd.com/t/topic/44114)）：Windows 版被踢更常见，Linux/Docker 版明显更稳；同账号在手机上保持登录的人，掉线明显少。
- NapCat issue [#1728](https://github.com/NapNeko/NapCatQQ/issues/1728)：新版 NapCat/QQ 登录会被风控检测导致频繁掉线。

注意：这些是**相关性**，不是因果。但它们指向同一个变量——**登录环境/客户端特征的一致性**。

## 三、SnowLuma 到底做对了什么（中证据，官方文档）

来源：[介绍](https://snowluma.github.io/zh/docs/guide/introduction)、[Windows 部署](https://snowluma.github.io/zh/docs/guide/deploy/windows)、[快速开始](https://snowluma.github.io/zh/docs/guide/quickstart)、[排障](https://snowluma.github.io/zh/docs/guide/faq)。

| 维度 | SnowLuma | 本项目现状 |
|---|---|---|
| 载体 | **真实 QQ 进程**（Win `QQ.exe` / Linux `qq`） | 真实 QQNT（pure shell 副本） |
| 接入方式 | native addon 做 **ptrace 级注入**，解析内部包 | 注入 hook DLL + **替换 app main（napcat.mjs）** |
| 登录方式 | **只支持扫码**，没有 CLI/密码登录 | 扫码 / 快速 / 密码 三选，实际每次都扫码 |
| 无头 | **不是无头**：Docker 里 Xvfb + noVNC 让 QQ"有桌面"，人肉扫码 | `CREATE_NO_WINDOW`，没有窗口 |
| 数据 | Docker volume：`/app/data`、`/app/.config`、`/app/.local/share`，**升级不丢登录态** | 散落在宿主机 `D:\QQ`，且没有版本迁移概念 |
| 版本 | hook 与 QQ 版本对齐，QQ 升级可能失效（要等适配） | 版本自带在包内，可回退 |
| 账号 | 一 UIN 一实例，自动检测 | 单实例 |
| 自我认知 | 文档明说"**容器重建可能换设备指纹 → 要重新扫码**" | 无此概念 |

**值得抄的 5 条：**

1. **只扫码**：不持有密码、不复用票据，登录动作和"用户本人在手机上确认"强绑定。
2. **先被动观察，登录完成后再接管**（`hookAutoLoad`：先 passive，扫码后切工作模式）——把"注入"和"登录"解耦，登录期间的客户端更像原版。
3. **数据卷与运行时分离**，升级只换运行时、不动数据目录。
4. **保留完整客户端**：Linux 上宁可用 Xvfb+noVNC 造一个桌面，也不砍掉渲染进程/窗口。
5. **版本对齐意识**：发行包固定 tag，QQ 升级要重新适配，而不是"随便一个版本硬注"。

**不能照搬的 2 条：**

1. Linux 容器 + VNC 那套不适合 Windows 桌面整合包（用户装完不会去开 VNC）。
2. 完整版只是"自带 Node.js"，**QQ 本体仍要用户自己装**——也就是说，SnowLuma 并没有解决"不依赖电脑自己装 QQ"，它解决的是"注入更干净、登录更克制"。这两件事要分开看。

## 四、回答"我能不能有自己的方案"

### 4.1 结论

**能，但要先接受三条硬约束**，否则方案一定会走回"掉了就重登"的死循环：

1. **登录态不能跨机器搬运**。票据/设备绑定 + 服务器侧记录，把 A 机的数据目录搬到 B 机，本身就是一次"设备突变"。所以整合包只能整合**运行时**，不能整合**登录态**；首次必须在本机扫码。
2. **客户端完整度 ≈ 安全度**。有窗口、有渲染进程、没有多余注入痕迹、版本别"既落后又旁路"，比任何"隐藏手段"都重要。
3. **掉线是"环境变了"，不是"程序坏了"**。所以自动化要做的是**少登录、稳登录、可续登**，而不是"踢了就立刻重扫"（频繁重登本身就是强信号）。

### 4.2 该有的形态（"整合包 2.0"）

```
运行时层（随包，只读）    QQNT 固定版本目录 + 注入层 + 运行时 + OneBot 桥
数据层（随包/随机器）     包内 QQData\（钉死，绝不落到宿主机 QQ 安装目录）
身份层（不可复制）        首次扫码建立，之后只做"续登"
观测层（GUI 一张表）      登录方式 / 掉线原因 / 存活时长 / 发送失败率
```

和第 1 节现状对照，缺的正是**数据层钉死**和**观测层**；`-q 10086` 则是把"少登录"直接做反了。

## 五、三档路线

### 档 A｜运维/配置档（零代码风险，先做）

| 动作 | 目的 |
|---|---|
| `napcat.quick.bat` 的 `10086` 换成真实 uin（或按策略干脆不带 `-q`，只走扫码） | 让"快速登录"真的可用，把"每次启动一次登录"降到"一天最多一次" |
| 把 QQ 数据目录钉进包内（先在一台干净机器实测 QQ 的落地规则） | 恢复"整合包"性质，顺带避免读写宿主机 QQ 安装目录 |
| 去掉 `--enable-logging` 之类多余调试参数；重新评估 `bypass` 各项 | 少一个"非默认启动"的特征 |
| 打开 NapCat 自身 `fileLog` | 现在掉线细节只有一行 console 文本，排障靠猜 |
| 启动顺序改成"先起 QQ → 等登录 → 再连 WS" | 登录期间不让 Python 侧反复打 WS |
| GUI 里显示"当前登录方式 / 掉线原因 / 上次掉线时间" | 把静默失败变成可见事件 |

预期：登录次数显著下降；掉线频次第一次变成可测量。

### 档 B｜结构档（对齐 SnowLuma 的工程约束，中等改动）

- **运行时与数据分离**：`versions/<ver>` 只读，配置和数据外置；换版本不丢配置。
- **启动器改造**：从"bat + 完全无窗口"改成"完整 launch，窗口可隐藏但**保留渲染进程**"；父子进程关系固定。
- **掉线状态机**：`KickedOffLine` / 心跳超时 / `call_action` 返回异常 → 三态（在线 / 掉线 / 进程死亡）→ 分级处置：重启 QQ 进程并尝试快速登录 → 失败则通知人工扫码，并**加退避**（不是每 3 秒硬撞）。
- **每台机器一个稳定 install id**：避免"每次装到不同路径"被当成新设备。
- **一 UIN 一实例**：为多账号留出口。

### 档 C｜自研协议档（不推荐）

就是"无头 QQ"那一派（Lagrange/icqq 路线）。SnowLuma 恰好反着走：真实客户端 + 注入。自研协议意味着没有官方上报与签名，风控面最大，且每次 QQ 升级都要重挖协议。

## 六、怎么验证"变好了"

| 指标 | 采集点 | 目标 |
|---|---|---|
| 登录方式分布（扫码/快速/密码） | NapCat 日志 + `fileLog` | 快速登录占比 ↑，扫码 ↓ |
| 登录后存活时长（P50/P90） | `KickedOffLine` − 登录时间 | 从"小时级"到"天级" |
| `KickedOffLine` 次数/天 | 现有日志即可 | 从 1~11 次/天 → ≤1 次/天 |
| 发送失败率（`call_action_sync` 返回 `None` / `retcode≠0`） | `api_client` | 降到接近 0 |
| A/B：`o3HookMode=1` vs `0` | NapCat 配置 | 看掉线是否减少 |

> 建议先做**只读统计**：把 10 月所有 `svc_napcat_*.log` 解析成一张"登录/掉线"时间表，作为基线。这个不改任何配置。

## 七、红线与法务

- **不要**改 `QQNT.dll` / `TSSafeEdit` / `QBar` 一类校验，也不要伪造设备指纹——那是把"灰"变成"明确对抗"，且会持续升级。
- **不要**把登录态（数据目录）打进整合包分发；这既不合法也不安全。
- 分发 QQ 二进制涉及腾讯许可：稳妥做法是**首次运行引导用户自行安装官方 QQ**（这也是 NapCat 上游默认行为），程序只做"检测 + 固定数据目录 + 注入"。
- README / 网盘页不要承诺"免登录""不封号"，把"首次需扫码、掉线需重扫"写清楚，减少用户预期落差。

## 八、还没确认、动手前必须先测的问题

1. **QQ 数据目录到底是怎么选的？** 本机注册表里只有 `HKCU\Software\Tencent\QQNT\version`，没有路径；但数据落到了 `D:\QQ`（本机 9.9.29 安装目录）。机制未定位 → **能不能钉进包内，必须在干净机器上实测**。
2. **`-q` 换成真实 uin 后，快速登录是否真的能成功？** 取决于票据是否还在数据目录里、以及 QQ 版本是否匹配。
3. **掉线是"被挤下线"还是"风控下线"？** 目前文案只有一种（登录失效），无法区分；需要 NapCat `fileLog` + 同账号手机端登录状态做对照。
4. **9.9.26 这个版本本身是否已被标记？** 本机装的 9.9.29 与包内 9.9.26 不一致，值得单独 A/B。
