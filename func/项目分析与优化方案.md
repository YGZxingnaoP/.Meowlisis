## 三、待实施方案（分析完成，未实施）

### 3.1 用户 ID 统一（一个用户 = 一个六位编号 = 多个平台账号）

**要解决的问题**
- 现在档案、聊天记录、待办、全员消息库全都挂在「用户名」这个字符串上。同一个人换昵称、或在 QQ 和 B 站同时出现，就会被当成两个人，档案各存一份
- 一个人还可能有声纹注册、B 站弹幕、QQ 聊天等多个身份，需要汇总到同一个人身上

**编号与目录**
- 每人一个六位编号，从 000001 开始顺序发下去，不回收、不复用
- 档案不再按名字放在 `character/info/users_info/` 下，改为 `character/userinfo/` 下一级按编号分文件夹：一个人一个文件夹，里面的 json 全部属于这个人
- 也就是：`character/info/users_info/{名字}_latest.json` → `character/userinfo/{编号}/profile.json`（历史备份 `profile-{日期}.json`、待办 `backlog.json` 同目录）
- **藏文件**（`.temp` 下那些按名字命名的记录）以后一律按用户 id 命名，名字不再出现在文件名里：`.temp/{编号}_record.txt`
- 现存的脏藏文件（实测有 `手机用户_record.txt`、`用户_record.txt`、`1025__record.txt` 这类）在迁移时清理掉
- 每个编号文件夹里放哪几个文件、文件怎么命名，动手前先出对照表给你确认，避免和现有读档案的代码对不上

**身份表**
- 一张对应表：编号 ↔ 昵称 ↔ 该编号下的各平台账号（QQ 号 / B 站 uid / 声纹名 / 以后新增的平台）
- 一张反查表：平台 + 账号 → 编号。查身份就是查这张表
- 一个平台账号只能属于一个编号；一个编号下同一平台只保留一个账号
- 代码位置：`func/catbrain/UserMemory/identity/`；数据文件：`character/userinfo/users.json`（对应表）与 `character/userinfo/index.json`（反查表），不另建 identity 目录
- 写入用临时文件替换 + 加锁，命令行和聊天同时改也不会写坏

**数据传递（必须走 pipeline）**
- 新增桥接 `func/pipeline/id_signup.py`（`IdSignupBridge`）：平台层（napcat / danmaku / sensevoice）与业务层取身份、执行指令、合并，一律调这个桥
- 任何模块不得直接引用身份表实现，数据传递全部经 pipeline
- 统一取身份入口就是 `IdSignupBridge().normalize(platform, account, name)`：有绑定回昵称，没绑定原样返回

**指令（前缀默认 `Meowlisis账号绑定`，前缀在「基本」里配一个词，不做开关）**

| 指令 | 谁发 | 干什么 |
|---|---|---|
| `前缀` 或 `前缀 帮助` | 任何人 | 列出全部子命令和参数 |
| `前缀 qq <QQ号>` | 在 B 站端发 | 把填的这个 QQ 号，绑到「当前发消息的这个 B 站账号」所在的用户 |
| `前缀 bili <uid或昵称>` | 在 QQ 端发 | 把填的这个 B 站账号，绑到「当前发消息的这个 QQ」所在的用户 |
| `前缀 声纹 <声纹名>` | 任意端 | 把声纹绑过来（声纹名取自声纹库） |
| `前缀 解绑 <平台>` | 本人 | 解绑自己名下该平台的账号 |
| `前缀 查看`（或 `前缀 id`） | 任何人 | 回自己的编号、昵称、已绑平台 |
| `前缀 昵称 <新昵称>` | 本人 | 改称呼（所有平台统一） |

- 方向就是子命令写的那个平台：在 B 站侧用 `qq` 绑 QQ，在 QQ 侧用 `bili` 绑 B 站
- 成功回明确结果（编号 + 昵称 + 绑了什么）；失败必须说清原因：参数缺失、QQ 号格式不对、B 站昵称反查不到或命中多条、该账号已被别人绑走（要提示现在属于谁）、当前平台不支持这个子命令、未绑定就执行解绑
- 指令只让发起人操作自己的账号；跨用户动作（合并、改别人的昵称）只走后端命令

**昵称（角色怎么称呼这个人，也是档案里的名字）**
- 取法：**优先用身份表里存的昵称**；没设过就沿用当前平台的 username，和现在完全一样（QQ 侧是对方 QQ 昵称、B 站侧是 B 站昵称、声纹侧是声纹名）
- 昵称存在身份表里，所有平台统一，用指令 `前缀 昵称 <新名>` 改
- 档案目录本身按编号走，昵称只用于显示与称呼，不参与找文件

**接入点（进大模型之前拦指令；取身份统一走一个入口）**
- QQ 私聊：`func/toolbox/napcat/napcat_core/event_handler.py`
- QQ 群 @：同文件
- B 站弹幕 / 醒目留言：`danmaku/web/web_client.py` 把账号带下来 → `danmaku/get_danmaku/get_danmaku.py` 存进缓存 → `danmaku/reply/reply_engine.py` 在回复前过指令
- 声纹：SenseVoice 侧拿到声纹名后走同一张表
- 统一入口：平台 + 账号 → 编号 → 昵称；取不到就退回原来的昵称字符串（不绑定时行为与现在完全一致）

**必须逐处核对的地方**
- `func/llm`：`llm_core.py`、`prompt_get.py`、`message_builder.py`、`state.py`
- `func/pipeline`：`system_prompt.py`（6 个 get_*_prompt 全部吃 username）、`llm_ltmem.py`、`msg_abmem.py`、`msg_database.py`、`sensevoice_llm.py`、`calendar_llm.py`、`toolbox_*.py`

- `func/toolbox/napcat`：`buffer.py`、`event_handler.py`、`qq_response.py`、`groupchat/*`（含已有那份昵称映射）、`active_sender/*`

- 口径：全项目带 `username` 的 py 约 100 个，真正要改的是上面这些「入口 + 提示词 + 落盘」，其余靠统一取身份那一层自动正确

**档案合并规则（按你定的）**
- 比 `affinity`（好感度，档案里就是 `affinity` 字段），**用高的那一份当底**
- 两边 `affinity` 一样，**优先用 B 站账号那一份**当底
- 当底那份的字段保留；另一份里当底缺的、或当底还是 `unknown` 的，才补进去
- 两份都有值又不一样，列出来给你选，不自动覆盖
- 合并对象不止档案本身：待办、短期记录、长期记忆里的归属标签、抽象记忆条目、档案历史备份，都跟着胜出那份走，重复的去重
- 合并前打印：双方编号 / 昵称 / 各平台账号 / `affinity` / 档案文件清单 → 你确认后才写；写前备份，可回退
- 不批量建档：现有 `users_info` 保持原样，合并是唯一入口

| QQ 私聊 | 文字私聊 | `napcat_core/api_client.py::send_private_text(user_id, 文本)` | 不进缓冲、不进大模型、不合成语音 |
| QQ 群 | 文字群聊并 @ 发起人 | 同文件 `send_group_at_text(group_id, at_qq, 文本)` | 同上；群里只放开「查看」与绑定类子命令 |
| B 站弹幕 | **文字弹幕** | `TBDanmakuWeb().send_danmaku_sync(文本)` | 不朗读、不走 TTS、不进大模型；只发文字 |

- 弹幕侧命中指令后必须在 `reply_engine.consume()` 里直接返回，**不能落到 `_reply_single` / `_reply_sc`**，否则就会走 `read_aloud` + TTS
- 弹幕文字有长度上限，帮助文本这类长回复要按长度切分、分条发送，并加发送间隔，避免被 B 站限流
- 发弹幕依赖网页登录态（`bili_jct`）；没配时发不出去，只能在日志里给出明确原因，同时提示去配置，不能静默失败
- QQ 侧和 B 站侧的回复文案尽量统一（同一套帮助文本、同一套失败原因），只在超长时按平台规则截断

**验收口径**
- 同一个人的 QQ 与 B 站账号绑到一起后，两个平台看到同一份档案、同一个昵称、同一套记忆
- 没绑定的用户，行为和现在一模一样

### 3.2 llm 的 toolbox / analysis 流程合并

**现状（割裂根因）**：主链路 `llm_core._ai_response` 的 `chat_stream` 不带 tools；工具链路另起一次调用（`MsgToolboxBridge → TBoxAnalysis.decide → llm.chat(tools)`，QQ 走 `TBNapcatAnalysis` 后再 `napcat_llm.reply`）→ 两次调用、两段上下文。

**可行性：可以**「先回复再调工具、思维链同一条」。`llm/port/deepseek.py::chat_stream` 已透传 tools，同一流可交错 `reasoning_content + content + tool_calls`；做法：主调用带 tools → 流式先出 content 照常播报，同时缓存 `tool_calls` → 若有则把 `assistant(content + tool_calls)` 追加进同一 messages、执行工具、追加 `role=tool`、续流收尾。

**前提 / 风险**：工具集需瘦身；避免 TTS 重复播报；NapCat 路径同理合并；跨 provider 流式 tools 需实测；`tool_choice` 用 `auto`。

### 3.3 CatPaws 合并（仅接口设计）

**现状**：`D:\.CatPaws` 是基于 WDA 的 iOS 局域网控制 —— `http_server`(:8080)；`wda_native_client` 连手机 :8100（tap/swipe/launch_app/screenshot，自动 scale）；`action_manager` 动态加载 `actions/*.py`（HTTP 模式不支持中途停止）；`screen/` 截图 / 坐标 / PaddleOCR。

**建议接口**（`func/toolbox/catpaws` 封装 :8080）
`phone_screen / phone_ocr / phone_tap / phone_swipe / phone_long_press / phone_repeated_tap / phone_launch_app / phone_activate_app / phone_run_script / phone_stop_script / phone_list_scripts / phone_write_script`
- OCR 驱动通用操作：截图 → OCR → LLM 决策坐标 → 动作 → 校验循环。
- 脚本缓存 + 实时更新：`actions/` 天然动态识别，加 registry + AI 生成/热更新 + OCR 差异检测。
- 全 AI 自主：写 / 改 / 选 / 执行 / 纠错全入 LLM 工具链。

**待确认**：仅 iOS？单/多手机？bundle_id 清单？是否改造成可中途停止？合并进 `func/toolbox/catpaws` 还是独立 `.vendor` 服务？
