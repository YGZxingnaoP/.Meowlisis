## 0. 先纠正一个前提：不是"每用户加载一个模型"

你说"按用户加载各自模型"。**参数不能按用户分**，否则显存直接炸：

| 方案 | 显存 | 说明 |
|---|---|---|
| 每用户一份 δ-mem 参数 | 14.68M × N × 4B = **每人 56MB**，100 人 5.6GB | 不可行，而且 100 份参数会训不起来（各自数据太少） |
| 参数一份 + 状态一人一份 | 参数 56MB（共享）+ 状态 **224KB/人**，100 人 22MB | 可行，已实现 |

**正确的说法是**：`load_model()` 只做一次（进程级），
`select_state(uid)` 每次生成前做一次（请求级）。
你写的协议里要传的是 **uid**，不是"模型名/权重路径"。

状态之所以能按用户分，是因为它只是 28 个 `r×r` 矩阵（r=64 时每层 4096 个数），
和注意力参数无关 —— 这也是 δ-mem 比 mem0 省的地方：**不用每人一份向量库+embedding**。

## 1. 目标目录布局

你现在的 `character/userinfo/` 是**扁平文件**（`index.json` + `000001.json` + `temp-000002.json`），
没有"每用户一个文件夹"。建议改成（或并存）：

```
character/userinfo/
├── index.json                    # "qq:xxx" -> "000001"（保持不变）
├── 000001/                       # ← 新建，正式用户
│   ├── profile.json              #   原 000001.json 搬进来（可选，能不动就不动）
│   └── mem/                      # ← δ-mem 状态
│       ├── delta_mem.pt          #   状态本体（bf16，224KB @ r=64 / 28 层）
│       ├── delta_mem.meta.json   #   指纹 + 衰减时间 + 写入日志（见 §1.1）
│       └── sources/              #   喂进去的原文快照（可追溯 / 可重建）
│           ├── 2026-10-19T14-03-00.md
│           └── 2026-10-24T09-11-32.md
└── temp-000002/                  # ← 只为对齐 index.json 存在；**mem/ 永不创建**
```

### 1.1 `delta_mem.meta.json` 必须有指纹

这是最容易出事的地方：换了权重、改了 rank、改了插入层，而旧状态还在，
加载后**不会报错**，只会静默输出垃圾。所以 meta 里必须有指纹：

```json
{
  "schema": 1,
  "cfg_fingerprint": "r64-n1-c16-Lall",        // rank/n_states/chunk/layers
  "weights_sha1": "3f9c...",                    // dmem.safetensors 的 sha1 前 12 位
  "backbone": "Qwen3-0.6B",
  "written_tokens": 8421,
  "written_at": "2026-10-24T09:11:32",
  "last_decay_at": "2026-10-24",                // 衰减用（将来）
  "writes": [                                    // 写入日志，可追溯/可回放
    {"at": "2026-10-19T14:03:00", "tokens": 4210, "mode": "replace", "src": "abmem+usrmem"},
    {"at": "2026-10-24T09:11:32", "tokens": 1102, "mode": "append",  "src": "session 42-51"}
  ]
}
```

**加载规则**：`cfg_fingerprint` 或 `weights_sha1` 不匹配 → **拒绝加载并记日志**
（不要自动迁移，也不要静默清零：前者会错，后者会丢记忆）。

## 2. 加载逻辑插在哪一层

三层可选，按侵入性从低到高。**建议 a + c 组合**：引擎层负责"换状态"，port 层负责"传 uid"。

### a) 引擎层（已实现，只管 owner→state）

```
engine.generate(messages, params)
      └─ self._apply_memory(params)          # params.memory_owner = uid
             ├─ registry.use(uid)            # 命中缓存 or 从 userinfo/<uid>/mem/ 读
             └─ dmem.enabled = True/False
```

`registry` 是唯一知道"状态文件放哪"的地方。要改成 userinfo 布局，
**只改 `DmemRegistry.path_of()` 一个函数**（现在是 `<state_dir>/<owner>.pt`，
改成 `<userinfo>/<uid>/mem/delta_mem.pt`），上层一行都不用动。这就是当初把
存储抽成 registry 的原因。

### b) 协议层（你想自己写的地方）

见 §3。协议只决定"uid 怎么传进来"，与状态存哪无关。

### c) port 层（`func/llm/port/*.py`）

每个 port 把"自己的协议字段"翻译成 openai 的 `extra_body`。见 §4。

## 3. 协议设计（推荐这套）

你的诉求是"自己写协议，各 port 适配"。给你一套最小但完整的：

### 3.1 关键取舍：**读走 header，写走 REST**

| 动作 | 通道 | 为什么 |
|---|---|---|
| 读记忆（生成时带 uid） | HTTP header `X-Mem-Owner: 000001` | header 天然透传、不污染 prompt、不影响 openai body 契约、日志里一行 grep 就能查 |
| 写记忆（记忆变了） | `PUT /mem/{uid}` REST | 写入文本可能几 KB，塞 header 会撞长度限制；而且"写"是低频事件，独立端点还能异步 |
| 遗忘 | `DELETE /mem/{uid}` | 与写对称 |
| 查状态 | `GET /mem/{uid}` | 运维用 |

**不建议**把记忆文本塞进 chat 请求体：一是每次请求都重复传（浪费），
二是会诱导你把记忆当 prompt 用（那就退回文本记忆了，δ-mem 的意义没了）。

### 3.2 协议定义（你说了要在 port 里适配，所以字段名自己定，下面是建议）

```http
POST /v1/chat/completions
X-Mem-Version: 1
X-Mem-Owner: 000001
X-Mem-Mode: read                # read | off  （write 走 REST，不在这里）
```

```http
PUT /mem/000001
Content-Type: application/json
{"text": "记忆流水文本…", "mode": "replace", "source": "abmem+usrmem", "dry_run": false}

→ 200 {"ok": true, "tokens": 4210, "chunks": 264, "seconds": 1.2,
       "fingerprint": "r64-n1-c16-Lall", "bytes": 229376}
```

```http
GET    /mem/000001     → {"exists": true, "written_tokens": 8421, "last_decay_at": "...", "stale": false}
DELETE /mem/000001     → {"ok": true, "removed": true}
```

约定三条：

1. **`X-Mem-Owner` 缺失 = 不挂记忆**（与今天行为一致，可随时降级）；
2. **`X-Mem-Owner` 是 temp-* → 服务端直接忽略**（不报错，不写盘）——
   过滤放在服务端，别指望每个 port 都记得过滤；
3. **`stale: true`** 表示指纹不匹配（权重换了）。这时服务端**不加载状态**，
   但仍返回 200 让对话继续 —— 记忆是增强，不能挡住出字。

### 3.3 为什么用 header 而不是 body 字段

`meowllm` 已经能解析 `extra_body.meowllm.memory_owner`（我上一轮加的）。
但你说要自己写协议 —— 那 **header 更合适**，理由是：

- body 是 OpenAI 兼容契约，加自定义字段容易和上游（真 deepseek / aliyun）行为冲突；
- 你的 port 层有 4 个（deepseek/aliyun/gemini/meowllm），header 只要在
  共用的 http client 上统一注入一次，body 字段则要逐个 port 处理；
- header 不会进 prompt，也不进 server 的 request hash（不影响 prefix cache 的键）。

`dmem_bridge` 的关键设计（这也是"按用户加载"真正的落地处）：

```python
def prepare(uid, force=False):
    """生成前调用：确保这个 uid 的状态是最新的。
    返回 owner 字符串或 None（None = 不挂记忆）。"""
    if not is_formal(uid):            # temp-* / 空 → None
        return None
    fp = mem_dir(uid) / "delta_mem.meta.json"
    if fp.exists() and fresh_enough(fp, tenant, ttl_hours=12) and not force:
        return uid                      # 12 小时内写过就不重写
    text = compose_memory_text(uid)     # abmem + user_memory + 近期对话摘要
    put_mem(uid, text, mode="replace")  # 走 REST，失败就 return None（降级）
    return uid
```

**去抖是必须的**：写一次 4k token 约 0.3~5 秒（GPU 状态而定），
每次对话都写会把延迟拉到不可接受。12 小时或"新增对话 ≥20 轮"才重写。

## 5. temp 用户过滤规则（集中一处，别散落）

```python
FORMAL = re.compile(r"^\d{6}$")          # 000001 / 000002 …

def is_formal(uid: str) -> bool:
    uid = str(uid or "").strip()
    return bool(FORMAL.match(uid))       # temp-000002 / local:主人 / qq:xxx 全部 False
```

**已核对的真实映射**（`character/userinfo/users.json` + `index.json`）：

| 账号 | uid | 定性 |
|---|---|---|
| **YGZ醒脑片** | **000001** | **主号**（`meowid: "000001"`，`qq:1149942002` / `bili:3546381505530135` 都指向它）→ 必须长期记忆 |
| Hgeminizjy 等 | 000002~000004 | 正式号 → 记忆 |
| `local:主人`（测试号） | temp-000009 | **测试用，不建 mem/ 目录** |
| 其余 temp-* | temp-0000xx | 跳过 |

所以 `^\d{6}$` 这条规则**天然就选中了主号 YGZ醒脑片（000001）、排除了测试号主人（temp-000009）**，
不需要额外"提升"。上线前只要确认 `users.json` 里 000001 的 `meowid` 没被改过即可。

## 7. 一句话

**参数一份、状态一人一份**：`load_model()` 一次，`select_state(uid)` 每次。
你要写的协议只需要表达"这次生成用谁的记忆"，三个动作（读 header / 写 REST / 遗忘 DELETE）就够；
存哪里由 registry 一个函数决定，改 `path_of()` 即可把状态搬到
`character/userinfo/<uid>/mem/`，并在 meta 里钉住权重指纹 —— 这样换权重时不会静默用错记忆。
