# 记忆召回实验室（memory_recall_lab）

> [English](README.en.md) | 中文

> **本目录只做实验，不参与主程序运行。** 主程序一行未改。
> 目标：用真实语料把「索引化」和「匹配召回」这两件事做成可对比、可复现的实验，
> 得出**当前最优的算法与参数**，而不是靠直觉改权重。

## 1. 为什么要有这个目录

主程序当前的召回（`func/catbrain/AbstractMem/load_abmem.py`）是一次全量线性扫描 + 一个加权和。
「记录一多就不准」到底是哪一环坏了、换成什么才好，光读代码给不出答案——必须有一把尺子。

这个目录就是那把尺子：真实语料 + 人工标注的评测集 + 多算法对照 + 网格搜索。

## 2. 文件

| 文件 | 作用 |
|---|---|
| `lab_core.py` | 语料加载、分词、四类索引（词倒排 / 字二元 / tag / 实体 / 月份）、BM25 |
| `lab_algo.py` | 各召回算法：现状基线、最小修复、五路混合、白守两种取法 |
| `lab_eval.py` | 指标、变体对照表、坐标下降网格搜索；输出 `lab_result.json` |
| `tune.py` | 在网格最优点附近做定向对照，输出「召回—精确—噪声—体积」权衡表 |
| `ablate_dict.py` | 单点消融：jieba 用户词典 vs 字二元通道 |
| `sweep_gate.py` | 闸门扫描：不设条数上限，只看相关性线定在哪 |
| `verify_production.py` | 校验主程序那份实现（`func/.../recall_index.py`）的实际表现 |
| `diagnose.py` | 逐查询诊断：漏的是「排序没进」「闸门挡了」还是「预算截了」 |
| `probe.py` | 标注辅助：列出每条查询的候选条目，供人工挑 gold |
| `goldset.json` | **评测集（唯一真值）**：21 条正例 + 14 条负例 |
| `lab_result.json` / `lab_tradeoff.json` | 运行结果落盘 |

## 4. 评测集是怎么来的（以及它的局限）

**构造方法**

1. `probe.py` 为每条查询列出「包含任一查询词」的候选条目（最多 8 条，按命中词数与 IDF 排序）。
   刻意**不用被测算法排序**，避免「用被测算法给被测算法出题」。
2. 人工逐条判定 `must`（核心答案）与 `ok`（相关但非答案）。
3. 负例三类：纯寒暄（随便/晚安/哈哈哈）、能力外问题（现在几点）、**硬负例**
   （「我电脑显卡是什么型号」——语料里有 5 条「显卡」但没有一条回答型号）。

**规模**：21 正例 + 14 负例，共 44 条 must。

**天花板**：`q02`（问「那首日语歌」，目标是《星降る海》）与 `q04`（问「那顿饭」，目标是「小鱼干外卖」）
与原记录**零字面交集**，任何词面方法都不可能召回。所以宏观召回的理论上限约 **0.905**，不是 1.0。

**局限（必须知道）**

- 单条 `must` 的判定由我人工完成，存在主观性；但 `must` 集合偏小（多为 1~4 条），误判影响可控。
- 432 条语料、35 条查询，规模小；结论的**方向**可靠，**具体阈值**需要用更大语料复核。
- 没有向量/语义通道（本机无 embedding 服务），因此「语义近义」类收益未被测量，天花板被低估。

## 5. 指标口径

均在同一预算 **top-k = 8** 下比较，避免「返回多所以命中多」的假优势。

| 指标 | 含义 |
|---|---|
| `recall_must` | 核心答案被召回的条数 / 核心答案总数（宏平均） |
| `prec_rel` | 召回结果中「核心 + 相关」占比（宏平均） |
| `mrr` | 第一条核心答案名次的倒数 |
| `漏答` | 正例里返回 0 条的个数 |
| `噪声` | 负例平均注入条数（理想 0） |
| `净召回` | 负例里返回 0 条的比例（理想 1） |
| `均条` / `字符` | 全部查询平均注入条数 / 按生产格式渲染的平均字符数 |
| `ms` | 单次召回耗时 |

综合分 = `F1(prec_rel, recall_must) − 0.3 × 噪声/8 − 0.02 × 漏答`。
用 F1 而不是加权和：加权和会被量纲与权重选择绑架，F1 对「召回高但全是噪声」（现状）和
「干净但漏答」（字二元单路）给出同样低的评价——这正是要的。

## 6. 结论：推荐方案

### 6.1 实测对照（432 条语料 / 35 条查询 / top-8）

| 方案 | recall | prec | mrr | 漏答 | 噪声 | 净召回 | 均条 | 字符 | ms |
|---|---|---|---|---|---|---|---|---|---|
| **现状（主程序）** | **0.722** | 0.298 | 0.565 | 0 | **8.00** | 0.00 | 30.0 | 875 | 10.5 |
| **★ 推荐**（词+tag+实体+时间） | 0.691 | **0.705** | **0.726** | 0 | **1.36** | 0.64 | **2.7** | **282** | **0.1** |
| 召回优先（推荐 + 字二元） | 0.714 | 0.657 | 0.676 | 0 | 2.00 | 0.07 | 3.2 | 332 | 0.1 |
| 最小修复（只改公式） | 0.528 | 0.706 | 0.528 | 5 | 0.93 | 0.64 | 2.1 | 227 | 9.7 |
| 只做字二元 | 0.325 | 0.861 | 0.476 | 9 | 0.71 | 0.64 | 0.9 | 95 | 2.6 |
| 白守式短路 | 0.000 | 0.000 | 0.000 | 21 | 0.00 | 1.00 | 0.0 | 7 | 0 |
| 白守式整句 LIKE | 0.000 | 0.000 | 0.000 | 21 | 0.43 | 0.93 | 0.2 | 24 | 0 |

**一句话**：召回基本持平（0.722 → 0.691，**−4%**；开字二元则为 0.714，**−1%**），
精度 0.298 → 0.705（**2.4 倍**），负例噪声 8.0 条 → 1.36 条（**−83%**），
注入体积 875 → 282 字符（**−68%**），耗时 10.5 ms → 0.1 ms（**约 100 倍**）。

> 上表「推荐」一行对应 `lab_algo.RECOMMENDED` 这个**冻结常量**；
> `tune.py`、`diagnose.py`、`ablate_dict.py` 都直接引用它，不读任何中间落盘文件。

> **可复现性**：召回链路里有「集合转字典 + 同分排序」，其顺序受 `PYTHONHASHSEED` 影响。
> 不固定种子时，同一配置每次跑出来的 recall 会差 **±0.03**——足够把好方案排到坏方案后面。
> 为此 `lab_core.py` 在首次导入时把种子固定为 0 并重启进程，无需外部设置。

### 6.1b 落地实现的实际表现

实验室只是设计空间；真正上线的是 `func/catbrain/AbstractMem/process/recall_index.py`。
`verify_production.py` 直接 import 主程序那份实现、跑同一套 goldset 校验。

**条数不设上限**——只保留一道相关性闸门，`summary_top_limit`（30）仅作最后兜底：

| 口径 | recall | prec | mrr | 漏答 | 噪声 | 均条 | 最多 | 字符 | ms |
|---|---|---|---|---|---|---|---|---|---|
| 旧方案（30 条固定预算） | 0.722 | 0.298 | 0.565 | 0 | 8.00 | 30.0 | 30 | 875 | 10.5 |
| **新方案 · 全量注入** | **0.865** | 0.492 | 0.629 | 0 | **1.71** | **5.8** | 19 | **611** | **0.12** |
| 新方案 · 同口径 top-8 | 0.746 | 0.493 | 0.621 | 0 | 1.71 | 4.5 | 8 | 472 | 0.12 |

两种口径都看：`top-8` 是用来跟旧方案公平对比（旧方案也只算前 8 条命中），
`全量` 才是模型实际看到的内容。

### 6.1c 闸门与上限是两件事

- **闸门（gate）**：`本条 BM25 ≥ 本批最高分 × recall_gate_ratio`，低于线的不出现。
- **上限（cap）**：条数截断。**已取消**，只留 `summary_top_limit` 兜底。

`sweep_gate.py` 在「不设条数上限」下扫闸门：

| gate_ratio | 均条 | 最多 | recall | prec | 噪声 | 字符 |
|---|---|---|---|---|---|---|
| 0.00（任何命中都算） | 8.9 | **70** | 0.881 | 0.431 | 1.71 | 931 |
| 0.02 | 5.9 | 19 | 0.865 | 0.497 | 1.71 | 614 |
| 0.30（当前默认） | 5.8 | 19 | 0.865 | 0.492 | 1.71 | 611 |
| 0.45 | 5.3 | 19 | 0.865 | 0.538 | 1.71 | 555 |
| 0.50 | 4.7 | 19 | 0.833 | 0.641 | 1.64 | 493 |
| 0.60 | 4.2 | 19 | 0.730 | 0.630 | 1.64 | 439 |

三条结论：

1. **闸门在 0.02–0.45 之间是平台期**，召回完全相同（0.865）。此时真正限制条数的是 tag 路，
   不是词路闸门——`q11「你怎么看我的价值观」` 注入 19 条，正好是语料里带「价值观」tag 的条数。
2. **ratio=0 会失控**：`q07「异环音乐教室…」` 一次注入 70 条（语料里 73 条提到异环），
   字符 931、精度掉到 0.431。所谓「相关性低得离谱才排除」，这个「离谱」仍然需要一条线。
3. **0.5 以上开始真的丢召回**（0.865 → 0.833 → 0.730）。默认取 0.30：处在平台期内侧，
   对陌生语料更宽容，同时避开 0 的失控。

另有一条：**核心锚点（实体/月份命中）单独用是坏的**——只走核心路时 recall 只有 0.345，
主力始终是关键词/标签那条补充路。所以核心路固定保留 5 条上限，不放开。

### 6.2 推荐配置

```python
k1 = 0.9            # BM25 词频饱和
b  = 0.5            # BM25 长度归一
field_weights = {"event": 1.0, "tags": 0.5, "joint": 0.3}

# 查询清洗（四步，全部确定性、无模型）
去停用词 → 丢弃纯数字 → 丢弃昵称碎片 → 丢弃 df > 10% 语料的词

# 通道
词 BM25  +  tag IDF  +  实体精确  +  回溯型时间窗
（字二元默认关；需要更高召回时开，代价是负例噪声翻倍）

# 融合：对称 RRF
score(d) = Σ_路 1 / (排名(d) + 60)

# 闸门
词路：bm25 ≥ 0.5 × 本批最高分        # 相对阈值，随语料规模自动缩放
tag 路：tag 的 IDF ≥ 3.5             # 压掉「日常/闲聊」这类话题同名 tag
实体/时间：命中即通过
字二元（若开）：IDF 和过线 且 至少命中 2 个二元组

# 预算
核心（实体/时间）≤3 条 + 补充 ≤5 条 = 硬上限 8 条
全灭时保底 1 条
```

### 6.3 三个关键设计点（都是实测逼出来的）

**① 相关性必须是连续量，不能是布尔量。**
现状 `hits / 1.0` 让「一个词命中 = 满分」，于是闸门失效、排序交给先验。
BM25 用 `idf × tf/(tf + k1·(1−b+b·|d|/avg|d|))`，「英语六级」这种稀有词自动高权，
「主人」这种 86% 记录都有的词自动趋零。

**② 闸门要用相对阈值，不能用固定常数。**
固定阈值（0.15 / 0.4 / 2.0）在语料从 432 涨到 4320 时必然失效：
候选集变大，分数分布整体右移，固定线要么全放行要么全拦死。
改成「本批最高分的 50%」或「本批候选的 P75」后，阈值随语料规模自动缩放——
这是治「记录越多越不准」的关键一招。

**③ tag 必须单独成路，不能塞进 BM25。**
tag 与话题高度共线（前四高频 tag 有三个就是话题名），塞进 BM25 会把 idf 拉到接近 0，
19 条「价值观」直接打平（实测目标记录被压到 BM25 第 16/18 位，等于全灭）。
单独成路后，命中 72% 只出现一次的稀有 tag 就是强信号。

## 7. 消融：什么没用，为什么

这些都是**实测否掉**的，记下来避免以后重复踩。

| 尝试 | 结果 | 原因 |
|---|---|---|
| **字二元作为独立通道** | F1 0.698 → 0.685；负例噪声 1.36 → 2.00；净召回 0.64 → 0.07 | 单字二元查询（「晚安」）只要命中一个二元组、按查询自身 IDF 归一化就是 1.0 —— 与 `hits/1.0` 是同一个饱和病。加了「至少 2 个二元组」约束后仍不够，它对负例是无差别放行。它确实把召回从 0.691 抬到 0.714，代价是 14 条负例里 13 条被灌进噪声 |
| **把 tag 词表灌进 jieba 用户词典** | F1 0.698 → 0.657 | 272 条 tag 短语被当成单个词，反而吞掉可匹配的子串（例：「介绍认识」合成一个词，查「认识」就搜不到了） |
| **只保留字二元单路** | 精度最高 0.861，但召回 0.325、漏答 9 | 它擅长精确匹配已知片段，不适合从零召回 |
| **白守式「名字有命中即短路」** | 召回 0.000，21 条正例全漏 | 评测集没有一条查询里出现已登记昵称；一旦名字不命中就完全不召回 |
| **白守式整句子串 LIKE** | 召回 0.000，21 条全漏 | 中文没有空格，整句当短语匹配几乎永不相交（这也解释了白守「混合检索」在中文上为何等于纯向量） |
| **「最小修复」只改公式** | 召回 0.691 → 0.528，漏答 5 | 公式改对了，但仍是 O(N) 线性扫且没有 IDF/tag 通道；证明**索引化不是可选项** |
| **字二元单路** | 精度 0.861（全场最高），但召回 0.325、漏答 9 | 擅长精确匹配已知片段，不适合从零召回 |
| **关闭 tag 通道** | F1 0.698 → 0.668 | 唯一能救「价值观/哲思」这类 tag 语义查询的路 |
| **闸门改绝对 P75** | F1 0.693 → 0.633 | 绝对阈值对分布变化不鲁棒；相对比例更稳 |
| **关闭实体/时间通道** | 无变化 | 评测集里没有「点名某人」或「去年这个时候」型查询——**这两条路的价值没有被本次评测覆盖**，不能据此认为它们无用 |

## 8. 与主程序对接时要注意

1. **索引必须挂在现有的写路径锁上。** 主程序 `save()` 是整月重写（`load_abmem.py:120-147`），
   索引更新若并发会读到半更新状态。
2. **注入格式也要瘦身。** 现状单行 104 字符里约 48% 是 `[话题｜标签｜参与｜时间]` 元数据；
   本实验的 `字符` 列按生产格式计算，已经包含这部分，所以 283 字符是含元数据的真实值。
3. **不要动写路径。** 432 条记忆里精确重复 0 组、近似重复 0 对，写入质量是好的。
4. **`joint` 字段键漂移**：425/478 条参与人条目用 `id` 键，而 `joint_util.resolve()` 只读 `meowid`。
   实验室的 `_joint_of()` 两种键都读；主程序需要同样修（否则实体通道对 89% 老记录失效）。
5. **切换必须用 shadow 模式**：先同时跑新旧两套、只记录不生效，用真实对话验证，
   因为注入条数从 30 降到 3 会改变模型行为——这是本次改动最大的风险，不是算法风险。

## 9. 如果要继续做

- **补向量通道**：本机没有 embedding 服务，语义近义（「英语六级」↔「六级考试」）未被覆盖。
  若加本地小模型（CPU 10ms 级），预计能把那 2 条硬负例和 2 条零交集正例补回来。
- **扩大评测集**：现在 35 条。建议扩到 150+ 条，并补充「点名某人」「去年这个时候」型查询，
  才能验证实体/时间通道的真实价值。
- **语料放大**：把 `.temp/public_short_mem.json` 之外的历史记录也纳入，测 2000+ 条下的表现。
