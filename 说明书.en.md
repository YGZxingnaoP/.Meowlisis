### 1. Optimizing LLM Filler Words

```
Corresponding modules:
func/llm/narration/
```

Idea: when an LLM reply is "watery" (all boilerplate and filler), compress it automatically; when the reply is rich, keep the vocal tics intact, so the synthesized speech doesn't sound wordy or flat. The core is a three-layer structure: score → tier → streaming cleanup:

1. **Filler-word dictionaries → Trie**: `adjunct_word.json` holds deletable words (used for both scoring and deletion), `score_only_word.json` holds score-only words (persona vocal tics); both build a Trie with longest-match-first lookup, O(word length).
2. **EWMA smoothed scoring** (each round uses the source text before cleanup):
   - `Raw = max(0, density − penalty)`
   - `density = 100 − (W/L)×100`, and when `W/L ≥ density_threshold`, `density = 0` (W = total filler-word length, L = text length)
   - `penalty = min(length_penalty_cap, max(0, L − length_threshold) × length_penalty_rate)`
   - `S = λ·S_prev + (1−λ)·Raw`, where `λ = λ_down (Raw<S) / λ_up (Raw>S) / λ_equal (Raw=S)`
3. **Three-tier streaming cleanup** (the tier is set by S):
   - `S ≥ part_level_upper` → delete nothing (FULL)
   - `part_level_lower ≤ S < part_level_upper` → delete only categories ∈ {2,3,5} (PART)
   - `S < part_level_lower` → delete every deletable word (ALL)
   - Character-by-character `feed`: longest Trie match, deletable words are dropped according to the tier, a matched prefix is held back for now; `flush()` finishes it off.
4. **Punctuation tidying**: after cleanup, runs of punctuation collapse into a full stop, leftover sentence-initial punctuation is removed, and punctuation-only sentences are never sent; the text is then split at punctuation into clauses and streamed into TTS, so the pauses sound natural.

Related config: `config.yml → llm.narration`.

### 2. Hum-and-Continue Song Trigger

```
Corresponding modules:
func/toolbox/meowsongs/hum_detect/hum_detect.py
func/toolbox/meowsongs/pass_the_baton
func/pipeline/toolbox_audio.py
```

Idea: while the character is singing, the user hums along for a bit; the character works out which song it is and how far the humming got, then **sings the next few lines** (passing the baton), announces its thoughts and writes it into memory.

1. **Hum detection**: frame-by-frame RMS energy; `rms ≥ vad_energy_threshold` (SenseVoice config) counts as voiced and accumulates, while silence `≥ silence_threshold` marks the end of a segment; accumulating `≥ hum_collect_sec(7s)` decides immediately. pyin extracts F0 (65–800Hz) → MIDI pitch, and only voiced frames are counted. The criteria are:
   - voiced-frame ratio: `|voiced|/|f0| ≥ f0_voiced_ratio`
   - stable-frame ratio: `mean(|Δmidi| < f0_stable_half_step) ≥ f0_stable_ratio`
   - unique note count: `len(unique(round(midi))) ≥ f0_unique_notes`
2. **Song lock in 7 seconds (lock)**: yin extracts F0 (80–800Hz) to get the hummed pitch sequence, mean-centers it together with each song's cached vocal pitch (npy) as `midi' = midi − mean(midi)`, then runs a vectorized sliding-window cosine `score = max_i dot(w_i,q)/(‖w_i‖·‖q‖)`; it only locks `{title, offset = best_idx×HOP/SR}` when `score ≥ match_threshold` and the gap to the runner-up is `≥ min_margin`.
3. **Continue singing at segment end (sing)**: the whole hum is matched again in one go, and the aligned position is the offset. The LRC timeline locates the lyrics: `user_lyric` = the lyrics inside `[offset, offset+hum_duration]`; take `hum_lines` lines starting from the first line after `offset+hum_duration`; play `vocal[start_sec : end_sec]` (end = the start of the next line, or the end of the song if there is none).
4. **Memory and thoughts**: the lyrics the user hummed and the lyrics the AI sang are written into short-term/long-term/user memory (type=hum_song); once the continuation finishes playing, the toolbox LLM generates a comment from a template (song title plus the sung lines) and speaks it; if nothing was locked or the margin was too small, the candidate songs and a "don't start singing yet" note go to the LLM with a `[System]` prefix, and the character confirms in its own words whether the user really is singing.

Related config: `config.yml → meowsongs.pass_the_baton`.

### Speech Recognition
Based on a heavily modified SenseVoice client (WebSocket to a local service, 2-pass streaming recognition, automatic reconnect after a drop)
 - Independent sessions per audio source: microphone / speaker loopback / injection source (phone voice, external PCM), each with its own VAD, barge-in and voiceprint
 - Noise filtering: VAD energy threshold, sound that's too quiet isn't recognized, configurable
 - Voiceprint detection: multiple voiceprint records, speakers matched by similarity threshold, recognition results bound to a user
 - Number normalization (itn), hot words, and error-prone word replacement rules
 - Real-time barge-in: a separate barge-in threshold that interrupts TTS as soon as speech is detected
 - Sentence merging (merge_delay), streaming display/synthesis
 - Speaker loopback is implemented (WASAPI, needs pyaudiowpatch), off by default, can be turned on under audio.sources.loopback
 - Phone/external audio is injected into the inject source over HTTP `/audio/send` (not through WebSocket); WebSocket audio transport isn't done yet

### Text-to-Speech
Based on a slimmed-down GPT-SoVITS(v2Pro), bundled, calling a local service over HTTP
 - Streaming synthesis: smart splitting at silence points (sounds continuous) or fixed-length splitting (fast response), with overlapping joins between chunks
 - Emotion-driven: the LLM decides an emotion label + intensity → emotion maps to reference audio + independent sampling parameters per emotion (happy speaks faster, sad slower, etc.)
 - Whole-segment language decision: all-English/all-Japanese overrides, mixed/Chinese falls back to Chinese (Chinese is the most stable by default)
 - Real-time barge-in: SenseVoice interrupts as soon as it detects speech; supports pipeline / key / off (pipeline needs SenseVoice)
 - Serial synthesis through a task queue (one background thread each for synthesis and playback)
 - Random pause between segments: by default 0.5~1s after each segment, can be turned off, can be set per source

### Memory Module
CatBrain multi-layer memory (func/catbrain), each layer with its own LLM backend (deepseek/aliyun/gemini)
 - Short-term memory: public_short_mem.json, trimmed by an independent turn count per message type
 - Long-term memory: written to disk per day as character/memory/<date>.txt, a full archive of the conversation
 - Memory summaries: record.txt in .temp triggers a summarize pass once it holds 50 messages, and the result is written per month as meow-YYMM.json; if summarization fails, the raw text goes back into the cache and waits for the next try
 - Summary write-in: three steps — categorize first, then search existing memories, then decide the relationship
 - Memory review: every new candidate is reviewed one by one and fails by default; passing requires a category and a confidence; whatever fails is dropped outright
 - Evidence score: every memory carries a credit score, both reinforcement and disputation decay by half-life, and ones that score too low are moved into the archive
 - Summary retrieval: sorted by total score, the top 30 go into the prompt; negative-scored and irrelevant ones are left out
 - Memory cleanup: cleanup_mem.py is run by hand when needed, by default it only looks and doesn't write, and only writes with --apply, backing up first
 - Current topic: decided periodically by the LLM (60s cache) and factored into summary ranking
 - User memory: new users get a profile guessed by the LLM, existing users are analyzed and updated every 50 turns (the AI can decide nothing changed and leave it)
 - Values: maintained by a separate LLM (high thinking effort), refreshed every 12 hours plus triggered by philosophical musing/conversation, with an optional second review
 - Message archive: everyone is recorded + vector store (embedding + keyword retrieval) + site retrieval

### Proactive Reply (llm_active)
The core of idle proactive replies, with cooldown timing, original topics and inherited topics, so the character speaks up when nobody is interacting. Code is in func/llm_active, config panel "Character proactive reply".
 - Timing: only fires once the idle time in `llm_active.cold_time` expires; user messages, AI replies and the end of a proactive trigger all reset the timer; paused while singing or while a plugin declares occupancy
 - Routing: while the consecutive trigger count `n` is within `strategy_threshold` it takes inherit (inherits the previous topic), beyond that it takes origin (the original topic pool: 5 topics + tags + cached Bilibili videos)
 - Material: origin's web_browse video pool (auto-scrape → LLM filtering → frame extraction → visual summary → saved to disk); Director planning reuses the same pool
 - Director first: `AutoActiveCore._trigger` asks `DirectorCore.on_idle_trigger` first; if the Director takes over, inherit/origin are skipped, and it falls back automatically on failure
 - Tunable: `llm_active.*` (cold_time, strategy_threshold, web_browse, director, etc.)
 - Difference from QQ: QQ has no idle timer, its proactive interjections are message-driven (@ / keywords / bubble-in) — see QQ Director below

### Director Module (llm_active.director)
Performance planning and execution during proactive replies, code is in func/llm_active/director; QQ doesn't use this one and has its own simplified version (see below).
 - Trigger: after each main-chain reply an async judge (pure LLM) decides "the master is bored / the topic has died" → it speaks up while skipping cold_time; when idle time expires the planner decides whether to start
 - Planning: director_plan outputs steps (goal / move / expect / if_not); it can read character/memory and reuse Bilibili video material
 - Execution: while active, user turns are taken over by func/pipeline/msg_director.py, reusing the main-chain reply logic, one step per turn
 - Advancing: director_step marks done / adjust / advance / clear; missed marks accumulate as `stall_turns` until a catch-up judgement; it wraps up when everything is done or the user clearly refuses
 - Loop: a whole idle stretch with no user message counts as one disappointment, and after `silent_rounds` in a row the plan is rewritten
 - Persistence: `.temp/director_topic/main.json`; clear archives to `character/director_topic/main/`
 - Prompt: `director_block.py` renders the plan into a "current conversation arc" block and splices it into system_prompt
 - Tunable: llm_active.director.*

### QQ Director (simplified, func/toolbox/napcat/director)
Serves only QQ private chats and group @ / keywords, and is completely independent of the main-chain Director: its own state file, judge and prompt block; it doesn't import the main-chain Director/Psyche state machine, and it takes no part in group proactive interjections (bubble-in).
 - Trigger: private messages, group @ or keyword hits (including the continued chat after them); bubble-in is excluded
 - Judgement: one small judge call before replying (through QQ's existing toolbox port) decides "is there no topic / should the current arc be wrapped up"; when there is no arc, a video previously shared from `character/shared_videos` is drawn at random as the lead, and the judge can see it
 - Arc: when the bit starts, 1~3 short steps are attached in a "current conversation arc (QQ · simplified)" block at the end of the QQ prompt; the lead is just an opener, not something to read out
 - Advancing: every line actually said on @ / keywords / private chat advances one step, and it closes automatically when they run out; the judge also closes it when it hears "stop bugging me / don't want to hear it", or when the other side picks the topic up
 - Isolation: `qq_private:{user_id}` and `qq_group:{group_id}` are stored separately, so a private chat never leaks into a group and a group never leaks into a private chat
 - Persistence: `.temp/director_topic/qq/{session}.json` (one file per private user / per group); after clear it archives to `character/director_topic/qq/{session}/` (the old `.temp/latest_director_qq.json` migrates automatically)
 - Tunable: napcat.director_qq.* (see "QQ Director" in the "NapCat group chat" config panel)

### Psyche State Machine (MeowPsyche)
What the character "is carrying in their heart right now". It records the inner state, not facts — facts belong to the memory summaries. Code is in the psyche directory under func, with its own LLM backend (deepseek, aliyun, gemini)
 - Trigger: a background thread glances at short-term memory every 5 seconds, and summarizes once each time the character adds a new reply
 - Input: the last 3 turns, plus the character's own previous psyche note, used only for contrast, never copied
 - Output: calls the note_inner tool and hands back one topic and up to four lines
 - Topic: the thing currently being done, and it must name who it is with. If you can't say what's being done, write empty — an empty topic wipes the whole block
 - Lines: only the character's own psyche, each starting from "I", covering emotions, what it wants, what it doesn't dare or can't do, and what it plans to do next
 - Injection: written to latest_psyche.json under .temp and stitched into the "what I'm carrying in my heart" part of the system prompt; both the main conversation and danmaku carry it
 - Scenes: main and QQ each keep their own state, with no effect on each other
 - Tunable: psyche.enabled, psyche.llm_type, psyche.interval_seconds, psyche.short_rounds

The four things it does each round:
```text
1 A new character reply shows up in short-term memory; it judges from the last utterance, so memory trimming doesn't matter
2 Take the last 3 turns plus the previous psyche note and hand them to the LLM together
3 Force a call to note_inner to get back a topic and lines
4 Write latest_psyche.json under .temp; if the topic is empty, clear the whole block
```

An example — the raw text produced by a real recording (the CET-6 listening session), as it looks once injected into the prompt:
```markdown
# What I'm carrying in my heart
Doing English listening practice with my master (the airport overbooking question)
I still want to laugh when I hear "volunteer", and sure enough my master latched onto it
I keep wondering whether he'll drag it back to Minecraft again
I'm holding back from dumping all the overbooking twists on him at once
I plan to wait until he asks once more before explaining the compensation part properly
```

The first line is the topic — the thing the character is actually working on right now — and the lines below are the character's own psyche. When it can't say what it's doing, the whole "what I'm carrying in my heart" section doesn't appear in the prompt.

The psyche block only writes "what I'm carrying in my heart", never where the conversation is going.


### User ID Module (MeowIdentity)
Every user gets an ID; nickname, QQ number and Bilibili uid all hang off that ID. The identity table is character/userinfo/users.json, the code is in func/catbrain/UserMemory/identity, and the entry point is func/pipeline/id_signup.py
 - ID: six digits, fixed the moment the account is opened. Nicknames may repeat; people are told apart by ID alone, and a reverse lookup by nickname refuses outright on duplicates
 - Binding: one ID can bind several platform accounts (QQ number / Bilibili uid); when both sides are bound they merge into one ID, and the ID doesn't move when accounts change
 - Reverse lookup: ID, nickname and account can all look each other up; anything unrecognized returns empty, and duplicates are never guessed
 - Temporary identity: anyone without a real ID yet gets temp-<id>; binding promotes it to a real six-digit ID and carries the accounts and nickname over
 - Offline identity: local machine names / voiceprint names only participate in resolution (local:, voice:) and are never bound
 - Storage: profile at character/userinfo/{id}/profile.json, backlog in the same directory, records in .temp/{id}_record.txt
 - Prompt: only nicknames appear in the prompt and the UI, IDs never enter the prompt

## Music (meowsinger / meowsongs)
Song requests and covers are in func/meowsinger; impromptu humming and hum-and-continue are in func/toolbox/meowsongs
 - Song request: prefix `Meowlisis点歌` ("Meowlisis, play a song") / intents `点歌、放歌、放首歌` ("request a song, play a song, put on some music") → search and download via the NetEase Cloud API → announce the title → play → end signal, with synced lyric subtitles; new messages that arrive while singing go into a summary pool and are answered together at the end
 - Cover: prefix `Meowlisis唱歌` ("Meowlisis, sing") / intents `唱首歌、唱歌` ("sing a song, sing") → RVC three-stem separation + voice conversion + mixing, with selectable model and feature index (the .RVC service); song-learning tasks run serially; results are stored in meow_list; falls back automatically when the remote RVC has no API; pitch/formant/volume are adjustable
 - Impromptu humming: the `impromptu_sing` tool, matching cover clips by lyrics (without accompaniment), with random/fuzzy/exact matching
 - Hum-and-continue: see "Original algorithm 2" in the README — hum_detect + pass_the_baton
 - Stop/learn: a stop word cuts the singing off immediately; learn triggers and learn users are configurable
 - Tunable: meowsinger.*, meowsongs.*

## QQ / NapCat (napcat)
NapCat is a OneBot v11 forward WS client, code is in func/toolbox/napcat, reply orchestration is in func/toolbox/qq_response.py, config node napcat
 - Connection: `napcat_core` (connection / event_handler / api_client / buffer); `ws_url` / `access_token`; `self_nickname` is used to recognize itself; for debugging, raw events can be dumped to `.temp/napcat_raw_events.jsonl`
 - Private chat: `receive_qq` → identity → Creeper → database → image-edit check → plugins → intent analysis (weather/news/backlog/impromptu humming/Turtle Soup/drawing, etc.) → armor-break → short/long-term memory → QQ Director → reply (`llm/napcat_llm`) → emote/emotion
 - Group chat: `receive_group` → Creeper → @+image → coordinator (`groupchat/group_coordinator`, 2-second merge by default) → directed (@/keywords) / followup (continued chat) / active (bubble-in)
 - @ / keywords: reply immediately; multiple people/triggers merge into one message inside the merge window; the `group_at` tool can @ group members separately; keyword hits get the same treatment as @; the QQ Director hooks in on @/keywords/continued chat (see above)
 - Continued chat: a followup judge decides whether to join in; the consecutive-pass cap, max reply turns and ignoring group bots are configurable
 - Bubble-in: whether to interject is decided by a message-count threshold + jitter + pass count; group bots such as 幻梦 can be called through `ask_group_bot`; bubble-in doesn't use the Director
 - Group record/group nature: `get_group_record` / `group_info` summarize periodically; group names, member profiles and group-bot settings all live here
 - Images/emotes: `image` (image_search / gif_frame / vision_decide), `message` (emote_choose / emote_sender / clean_emote / quote_store / time_split)
 - Active sending: `active_sender` (friend/group/group-member lists, send text/file/link), with cooldown
 - Diagnostics/login-state observation: [scripts/napcat_diagnose/README.en.md](scripts/napcat_diagnose/README.en.md)
 - Others: `poke_detector`, `creeper`, `excuse_router`, `emotion_bridge`, `identity/qq_cmd`, `identity/qq_send`, `psyche`, `vision_active`, `director` (QQ Director)
 - Tunable: napcat.* (reply length/punctuation/quoting/rhythm, images, emotes, keywords, merging, continued chat, bubble-in, group info, group bots, Director)

## Holiday Greetings (calendar)
Code is in func/calendar
 - Holiday data: `holiday.json`, covering fixed Gregorian holidays, lunar-calendar holidays, the 24 solar terms and floating holidays (Mother's Day/Father's Day, etc.)
 - Greeting text: `greeting.json` configures templates per birthday/holiday/solar term, falling back to a default template; priority birthday > holiday > solar term
 - Trigger: the greeting is only consumed when the user speaks for the first time that day; with `mark_first=False` only the date info is kept and no greeting is decided; birthdays come from the user profile

## Memory Curation (catbrain)
Abstract memory, user memory and long-term memory work together in layers, with scheduled summarization and tidying, still being optimized.
 - Summaries: a full record cache triggers a summarize pass, archived by month; on failure the raw text is written back and retried next time
 - User profile: new users get a guessed profile, existing users are updated incrementally by turn count; values are maintained by a separate thread
 - Cleanup: cleanup_mem only looks by default and doesn't write, only runs with --apply, and backs up before writing
 - Recall experiments: [scripts/memory_recall_lab/README.en.md](scripts/memory_recall_lab/README.en.md)

## Phone Control
Let the character handle things on a phone itself: the PC runs WebDriverAgent on an iPhone over a USB tunnel (see [CatApps_iOS](https://github.com/YGxingnaoP/CatApps_iOS) for the modified version), and the character looks at the screen, taps, types and turns pages while talking as it goes. Maps to `func/catpaws` (intent judgement and voice/memory bridging only, it doesn't touch the LLM) and `.vendor/.CatPaws` (its own LLM, action chain, action scripts, screen streaming); the source of truth for config is `.vendor/.CatPaws/config.yml`.

- Trigger: saying "喵呜我要点外卖" ("meow, I want to order takeout") goes straight into the chain; merely mentioning intent words like "phone" first lets the LLM decide whether to take over
- Operations come in three kinds: one-shot (tap once, swipe once, back), continuous (several steps dispatched at once, 90ms apart by default), and action scripts (a fixed flow is distilled into `actions/<id>/`; whatever is written during the reflection stage needs the master to nod twice)
- Wrap-up: when it's done it first asks "anything else?", and after confirmation goes into reflection to distill a script; payment, password and privacy-type operations are forbidden across the whole chain
- Speech and memory: replies on the phone side are spoken in the character's voice and also written into short-term memory (`phone_control_user` / `phone_control_response`), long-term memory and user memory
- GUI: the phone-control panel has a live view, the operation log, a config panel and a start button; opening `https://<PC-IP>:8443` in a phone browser shows the desktop pet
- Standalone debugging: `scripts\catpaws\catpaws_device_test.bat` opens two windows ("chat + log") and can drive a real device directly, without starting the main program
- Details: CatPaws service [.vendor/.CatPaws/README.en.md](.vendor/.CatPaws/README.en.md); launcher [.vendor/.CatPaws/catpaws-launcher/README.en.md](.vendor/.CatPaws/catpaws-launcher/README.en.md); debugging scripts [scripts/catpaws/README.en.md](scripts/catpaws/README.en.md); phone UI [.vendor/.cam/README.en.md](.vendor/.cam/README.en.md)
